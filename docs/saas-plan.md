# แผน SaaS หลายบริษัท / หลายสาขา

สถานะ: **แผนพร้อมเริ่ม (2026-10-10)** · ยังไม่เริ่มทำ · ข้อตัดสินใจ D1–D7 ยืนยันครบแล้ว (2026-10-10) — ประเด็นภาษี / บัญชียังให้นักบัญชีตรวจทาน (หัวข้อ 11, 13, 15)

เป้าหมาย: ระบบเดียวให้หลายบริษัท (tenant) ใช้ร่วมกัน แต่ละบริษัทมีได้หลายสาขา
ข้อมูลต้องแยกขาดระหว่างบริษัท และรายงาน / สต็อก / เอกสารต้องแยกตามสาขาได้

ตอนนี้ระบบเป็นร้านเดียว: `StoreInfo` มีชุดเดียว, `Product.stock` / `avgCost` เป็นค่ารวม,
`User.role` มีแค่ `admin | user`, เลขเอกสาร (`POS-`, `INV-`, `CN-`) รันชุดเดียว

## 1. โครงสร้าง

```
Platform (เจ้าของ SaaS)
└─ Company / Tenant      รหัสบริษัท (ใช้ตอน login), เลขผู้เสียภาษี 13 หลัก, จด VAT, แพ็กเกจ, subdomain (ภายหลัง)
   ├─ Branch (สาขา)       รหัสสาขาสั้น (เช่น BKK01) + เลขสาขาสรรพากร 5 หลัก (00000 = สำนักงานใหญ่)
   │  └─ POS terminal    เลขเครื่อง POS ที่สรรพากรออกให้ (ต่อเครื่อง)
   └─ User               สังกัดบริษัท, role, สาขาที่เข้าได้
```

- 1 บริษัท = 1 เลขผู้เสียภาษี บริษัทในเครือที่เลขภาษีต่างกันถือเป็นคนละ tenant
- สาขามีทั้งรหัสสาขาสั้นที่ใช้ในระบบและเลขเอกสาร (`code`, ไม่ซ้ำภายในบริษัท) และเลขสาขาสรรพากร (`branchNo`)

## 2. การแยกข้อมูลและความปลอดภัย (กฎหลัก)

1. **`tenantId` มาจาก token เท่านั้น** ห้ามรับจาก URL, query หรือ body ไม่ว่ากรณีใด
2. ฐานข้อมูลใช้ร่วมกัน แต่ทุกตารางมี `tenant_id` + เปิด **Row-Level Security** (PostgreSQL):
   ต้นทาง request ตั้ง `SET app.tenant_id` แล้ว policy กรองให้ ลืมใส่ `WHERE` ก็ไม่หลุดข้ามบริษัท
   ลูกค้าองค์กรย้ายไปฐานข้อมูลแยกได้ภายหลัง (D7, หัวข้อ 16)
3. JWT claims: `sub` (userId), `tenantId`, `role`, `branchIds` (หรือ `allBranches: true`)
4. **สาขาที่ทำงานอยู่** ส่งใน header `X-Branch-Id` ทุก request และ server ต้องตรวจว่าอยู่ในสิทธิ์
   (ไม่อยู่ → 403) งานประจำวัน (ขาย, รับเข้า, ตัดสต็อก) ทำได้กับสาขานี้เท่านั้น
5. รายงานที่ดูข้ามสาขาใช้ query `?branchId=<id>|all` แยกจาก header แล้ว server ตรวจสิทธิ์เหมือนกัน
   (`all` ได้เฉพาะ role ระดับบริษัท)
6. ทุก unique key รวม `tenant_id` เช่น รหัส SKU และ `username` ไม่ซ้ำ **ภายในบริษัท** (บริษัทอื่นใช้รหัสเดียวกันได้)
   รวมถึงบาร์โค้ด, รหัสผู้จำหน่าย และเลขเอกสาร
7. Audit log ระดับ tenant: ใคร / สาขาไหน / ทำอะไร / เมื่อไร (void, ส่วนลดพิเศษ, ออกใบกำกับใหม่, ปรับสต็อก)

## 3. ข้อมูลระดับบริษัท / ระดับสาขา

| ข้อมูล (model ปัจจุบัน)                                  | ระดับ          | หมายเหตุ                                                                                                                                                                                      |
| -------------------------------------------------------- | -------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Product` (SKU master), `Category`, `Supplier`, บาร์โค้ด | บริษัท         | ทุกสาขาใช้รหัสเดียวกัน                                                                                                                                                                        |
| `Product.saleStatus`                                     | บริษัท         | (อนาคต: เปิด/ปิดขายรายสาขา)                                                                                                                                                                   |
| `Product.stock`, `avgCost`, `minStock`, `maxStock`       | **สาขา**       | ตาราง `branch_stock (tenant, branch, product)` — ดูหัวข้อ 4                                                                                                                                   |
| `SerialNumber`, `StockMovement`                          | **สาขา**       | serial มี `branchId` (อยู่ที่สาขาไหน)                                                                                                                                                         |
| `SkuPrice`                                               | บริษัท         | ราคาเดียวทั้งบริษัท (D2); ราคาเฉพาะสาขาค่อยเพิ่ม `branchId` ที่เว้นว่างได้ภายหลัง                                                                                                             |
| `Promotion`                                              | บริษัท         | + `branchIds` (ว่าง = ทุกสาขา) ตาม D2; สร้าง/แก้ได้เฉพาะ owner / admin ระดับบริษัท                                                                                                            |
| `PaymentMethod`                                          | บริษัท         | สาขาปิดบางช่องทางได้, `promptPayId` / `bankAccount` อาจต่างตามสาขา                                                                                                                            |
| `User`                                                   | บริษัท         | + `username` (ไม่ซ้ำในบริษัท), `email` ไม่บังคับ (owner ต้องมี), `branchIds` / `allBranches`                                                                                                  |
| `StoreInfo`                                              | **แยก 2 ส่วน** | `CompanyInfo`: name, taxId, vatRegistered, exchangeDays, manualDiscountMaxPercent, taxInvoicePaper · `BranchInfo`: code, placeName, branchType/branchNo, address, phone, posId, receiptFooter |
| `Sale`, `CreditNote`, `Exchange`, `TaxInvoice`           | **สาขา**       | + `branchId` (snapshot ชื่อ/เลขสาขาในเอกสาร)                                                                                                                                                  |
| เลขรันเอกสาร                                             | **สาขา**       | `POS-<code>-YYYYMMDD-NNNN`, `INV-<code>-…`, `CN-<code>-…`, `EX-<code>-…`                                                                                                                      |
| พักบิล POS (localStorage)                                | เครื่อง + สาขา | key รวม tenant + branch: `pos.held.<tenantId>.<branchId>`                                                                                                                                     |

## 4. สต็อกและต้นทุน

- **ทุนเฉลี่ยเคลื่อนที่คำนวณแยกต่อสาขา** (D1 ยืนยัน 2026-10-10) (1 สาขา = 1 คลัง) บัตรสต็อกจะเป็นรายสาขา
  ส่วน Serial ใช้ทุนเฉพาะเครื่อง (specific identification) อยู่แล้วจึงไม่กระทบ (ข้อตัดสินใจ D1)
- API คืน `Product` **หน้าตาเดิม** โดย server เติม `stock` / `avgCost` / `minStock` / `maxStock`
  ของสาขาใน `X-Branch-Id` ทำให้หน้าคลังสินค้า, POS, reorder และ export Excel แทบไม่ต้องแก้
- หน้าสต็อกรวมทุกสาขา (ใหม่): `GET /products/:id/branch-stock` → `[{ branchId, stock, avgCost }]`
- **ใบโอนสินค้า** (เอกสารใหม่ `TR-<code>-YYYYMMDD-NNNN`):
  1. สร้างที่สาขาต้นทาง → ตัดออกที่ทุนเฉลี่ยของต้นทาง (serial: ทุนของเครื่อง) สถานะ `in_transit`
  2. สาขาปลายทางกดรับ → รับเข้าที่ทุนนั้น (non-serial เข้า `movingAverage()` ของปลายทาง) สถานะ `received`
  3. รับไม่ครบ / เสียหายระหว่างทาง → บันทึกส่วนต่างเป็น write-off พร้อมเหตุผล
  - ระหว่างทาง serial มีสถานะ `in_transit` (ขายไม่ได้ทั้งสองสาขา)
  - movement ใหม่ 2 ชนิด: `transfer_out` / `transfer_in`
- แนะนำสั่งซื้อ (`suggestReorderQty()`) คิดต่อสาขาจาก min/max ของสาขา

## 5. ภาษีและเอกสาร (ให้นักบัญชียืนยัน)

- ใบกำกับภาษีทุกแบบพิมพ์ **สาขาผู้ขาย** ของสาขาที่ออก (`branchLabel()` จาก `BranchInfo`)
- **รายงานภาษีขายทำแยกตามสถานประกอบการ** (`/sales/tax-report?month=&branchId=`) หัวรายงานใช้ชื่อสถานประกอบการและเลขสาขาของสาขานั้น
  ยื่นรวม (ได้รับอนุมัติ) = ทำทีหลัง เปิดด้วยค่าตั้ง `CompanyInfo.vatFilingCombined`; ระหว่างนี้มีแค่ตารางสรุปทุกสาขา "ไม่ใช่รายงานยื่นภาษี" (D6, หัวข้อ 15)
- ใบลดหนี้ / ใบเปลี่ยนสินค้า / void ทำได้เฉพาะที่สาขาที่ขาย (D3, หัวข้อ 13) — ใบลดหนี้ลงรายงานภาษีของสาขาที่ขาย
- เลข POS (`posId`) อยู่ระดับสาขา ถ้าในอนาคตมีหลายเครื่องต่อสาขา ให้แยกเป็น `PosTerminal`
- `buildSalesTaxReport()`, `invoiceTotals()`, `draftCreditNote()` ไม่ต้องเปลี่ยนสูตร แค่ข้อมูลที่ส่งเข้าไปถูกกรองตามสาขา

## 6. ผู้ใช้และสิทธิ์

| role             | ขอบเขต                 | ทำได้                                                           |
| ---------------- | ---------------------- | --------------------------------------------------------------- |
| `platform_admin` | ทุก tenant             | จัดการบริษัท, แพ็กเกจ, ระงับการใช้งาน (หน้าแยก ไม่ปนกับแอปร้าน) |
| `owner`          | บริษัท                 | ทุกอย่าง + ตั้งค่าบริษัท, สาขา, การเก็บเงิน                     |
| `admin`          | บริษัท / สาขาที่ได้รับ | = `admin` ปัจจุบัน (ใบลดหนี้, ออกใบกำกับใหม่, ส่วนลดไม่จำกัด)   |
| `user`           | สาขาที่ได้รับ          | = `user` ปัจจุบัน (แคชเชียร์ / คลัง)                            |

- `User` เพิ่ม `username` (ไม่ซ้ำภายในบริษัท), `email` ไม่บังคับ (ยกเว้น owner), `branchIds: number[]` และ `allBranches: boolean`
- กฎ "admin only" เดิมทั้งหมดใช้ต่อได้ แต่ต้องตรวจคู่กับสิทธิ์สาขาด้วย
- login ด้วย **รหัสบริษัท + ชื่อผู้ใช้ + รหัสผ่าน** (D4, หัวข้อ 14); 1 บัญชี = 1 บริษัท (D5)

## 7. API (เปลี่ยน / เพิ่ม)

- `POST /auth/login { companyCode, username, password }` → `{ token, user, company, branches }` (`branches` = สาขาที่ user เข้าได้) · platform admin login ผ่าน endpoint แยก
- `GET /me` → เหมือนข้างบน (ใช้ตอนโหลดหน้าใหม่ หลังสลับสาขา)
- ทุก endpoint เดิมรับ header `X-Branch-Id` endpoint ระดับบริษัท (SKU, หมวด, ผู้จำหน่าย, โปร, ช่องทางชำระ, ผู้ใช้) ไม่สนใจค่านี้
  ยกเว้นเวลาเติมฟิลด์ stock ของสาขาใน `Product`
- รายงาน: `GET /sales`, `/credit-notes`, `/tax-invoices`, stock card รับ `?branchId=<id>|all` (ไม่ส่ง = สาขาใน header)
- ใหม่:
  - `GET/POST /branches`, `GET/PUT /branches/:id` (ปิดใช้งานแทนการลบเมื่อมีเอกสาร)
  - `GET/PUT /settings/company`, `GET/PUT /settings/branch` (แทน `/settings/store`)
  - `GET /products/:id/branch-stock`
  - `GET/POST /transfers`, `GET /transfers/:id`, `POST /transfers/:id/receive`
- `GET/PUT /settings/store` เก็บไว้ช่วงเปลี่ยนผ่าน (= company + branch ปัจจุบันรวมกัน) แล้วค่อยถอด

## 8. ผลกระทบต่อหน้าบ้าน (repo นี้)

**core**

- `core/models/company.model.ts` (ใหม่): `Company`, `Branch`, `CompanyInfo`, `BranchInfo`, `branchError()`
  แยก `store-info.model.ts` ออกเป็น 2 ส่วน และให้ `StoreInfo` เดิมเป็นค่าที่ประกอบกลับ (`CompanyInfo & BranchInfo`)
  เพื่อให้ `Receipt` / `TaxInvoiceDocument` / รายงานภาษีไม่ต้องแก้
- `user.model.ts`: role ใหม่, `branchIds`, `allBranches`
- `AuthService`: เก็บ `company`, `branches` และสาขาปัจจุบัน (`StorageService` key `branch`); รหัสบริษัทที่เครื่องจำไว้ (key `companyCode`) ไม่ถูกล้างตอน logout
  ถ้ามีสาขาเดียวให้เลือกอัตโนมัติ
- `branchInterceptor` (ใหม่): ใส่ `X-Branch-Id` ลำดับ: loading → auth → **branch** → error → mockBackend
- การเลือกสาขา: หน้า `/select-branch` ใน `AuthLayout` (หลัง login เมื่อเข้าได้มากกว่า 1 สาขา)
  ตัวสลับสาขาบน toolbar ของ `MainLayout` → `document.location.reload()` (ตรงกับกฎ SPA ต่อเมนู: state ในหน่วยความจำล้างเอง)
- toolbar แสดง "บริษัท · สาขา" ตลอดเวลา เพื่อกันขายผิดสาขา

**features**

- `master-data`: แท็บใหม่ **สาขา**
- `settings`: แยกเป็นตั้งค่าบริษัท / ตั้งค่าสาขา
- `inventory`: เมนูย่อยใบโอนสินค้า (`/inventory/transfers`), ดูสต็อกทุกสาขาจากหน้ารายการ
- `sales`: ตัวเลือกสาขาในรายการบิลและรายงานภาษี (role ระดับบริษัทเลือก "ทุกสาขา" ได้ ยกเว้นรายงานภาษีที่ต้องเลือกทีละสาขา + ตารางสรุปภาษีขายทุกสาขาสำหรับ owner / admin ระดับบริษัท); ปุ่มคืน / เปลี่ยน / void ใช้ไม่ได้กับบิลของสาขาอื่น (D3)
- `pos`: key พักบิลรวม tenant + branch; เลขบิลมีรหัสสาขา (server ออก)
- `promotions`: เลือกสาขาที่ใช้โปร (ว่าง = ทุกสาขา) ในฟอร์ม + คอลัมน์สาขาในรายการ
- `users`: กำหนดสาขาที่เข้าได้
- dashboard: ตัวเลือกสาขา / รวม

**mock**

- `an22.mock.db` เพิ่ม `companies`, `branches`, `branchStock`, `transfers` และ `branchId` ในเอกสาร
- mock อ่าน `X-Branch-Id` + tenant จาก token ปลอม
- seed: 1 บริษัท 2 สาขา (สำนักงานใหญ่ + สาขา 00001)
- ข้อมูลเดิมที่เก็บไว้ → ย้ายเข้าสาขาแรกตอนอ่าน (ตามแนว `PRODUCT_DEFAULTS` merge)

## 9. ลำดับงาน (แต่ละขั้น build + test + lint ผ่าน แล้ว commit)

1. **วางฐาน (ยังเป็นสาขาเดียว)**
   - หลังบ้าน: schema `tenant_id` / `branch_id` ทุกตาราง + RLS + JWT claims
   - หน้าบ้าน: `company.model.ts`, `AuthService` เก็บบริษัท/สาขา, `branchInterceptor`, toolbar แสดงบริษัท · สาขา
   - mock: 1 บริษัท 1 สาขา
2. **ข้อมูลสาขา**: แท็บสาขาใน master-data, แยก `StoreInfo` → `CompanyInfo` + `BranchInfo`, settings 2 หน้า,
   ผู้ใช้กำหนดสาขาได้, หน้าเลือกสาขา + ตัวสลับ, โปรโมชั่นจำกัดสาขา (`branchIds`)
3. **สต็อกแยกสาขา**: `branch_stock`, serial/movement มีสาขา, ทุนเฉลี่ยต่อสาขา, reorder ต่อสาขา, ดูสต็อกทุกสาขา
4. **เอกสารแยกสาขา**: เลขรันต่อสาขา, ใบกำกับพิมพ์สาขาผู้ขาย, ตัวกรองสาขาในรายการบิล, รายงานภาษีขายต่อสาขา + ตารางสรุปภาษีขายทุกสาขา (D6)
5. **ใบโอนสินค้าระหว่างสาขา**
6. **ส่วน SaaS**: สมัครใช้งาน / onboarding (สร้างบริษัท + สาขาแรก + owner), แพ็กเกจ + จำกัดจำนวนสาขา/ผู้ใช้,
   การเก็บเงิน, หน้า platform admin, subdomain (ถ้าเลือก), export ข้อมูลทั้งบริษัท + ขั้นตอนลบข้อมูลเมื่อเลิกใช้ (PDPA), audit log

- **D4** ✅ ยืนยัน 2026-10-10: login ด้วย **รหัสบริษัท + ชื่อผู้ใช้ + รหัสผ่าน** เครื่องจำรหัสบริษัทไว้; subdomain ทำทีหลัง (รายละเอียดหัวข้อ 14) — เปลี่ยนจากค่าแนะนำเดิม "อีเมลไม่ซ้ำทั้งแพลตฟอร์ม" เพราะพนักงานหน้าร้านมักไม่มีอีเมล
- **D5** ✅ ยืนยัน 2026-10-10: **1 บัญชี = 1 บริษัท** (ตามมาจาก D4: ชื่อผู้ใช้ผูกกับบริษัท ทำงานสองบริษัท = สองบัญชี)
- **D6** ✅ ยืนยัน 2026-10-10: รายงานภาษีขายที่ใช้ยื่น **ทีละสาขาเท่านั้น** + ตารางสรุปทุกสาขา (ไม่ใช่รายงานยื่นภาษี); รายงานยื่นรวมทำทีหลังผ่านค่าตั้ง `vatFilingCombined`; รายงานภาษีซื้อนอกขอบเขต (รายละเอียดหัวข้อ 15)
- **D7** ✅ ยืนยัน 2026-10-10: **ฐานข้อมูลเดียว + `tenant_id` + RLS**; ทะเบียนบริษัทเก็บว่าใช้ฐานไหน เพื่อย้ายลูกค้าองค์กรไปฐานแยกได้ภายหลัง; export / ลบข้อมูลทั้งบริษัทอยู่ในขั้นที่ 6 (รายละเอียดหัวข้อ 16)

## 11. รายละเอียด D1 — ทุนเฉลี่ยแยกต่อสาขา (ยืนยันแล้ว 2026-10-10)

ใช้กับสินค้าที่**ไม่มี Serial** เท่านั้น (ถัวเฉลี่ยเคลื่อนที่: รับเข้าครั้งใดคำนวณทุนเฉลี่ยใหม่ ขายตัดทุนที่ค่าเฉลี่ยขณะนั้น)
สินค้า Serial ใช้ทุนของแต่ละเครื่องอยู่แล้ว จึงไม่ได้รับผลจากข้อนี้

### ตัวอย่าง: เมาส์รุ่นเดียวกัน

- สาขา A ซื้อ 10 ชิ้น ชิ้นละ 100 บาท
- สาขา B ซื้อ 10 ชิ้น ชิ้นละ 130 บาท (ซื้อทีหลัง ราคาขึ้น)

|                                 | แยกต่อสาขา | รวมทั้งบริษัท |
| ------------------------------- | ---------: | ------------: |
| ทุนเฉลี่ยสาขา A                 |        100 |           115 |
| ทุนเฉลี่ยสาขา B                 |        130 |           115 |
| A ขาย 1 ชิ้น ตัดทุน             |        100 |           115 |
| B ขาย 1 ชิ้น ตัดทุน             |        130 |           115 |
| มูลค่าคงคลังรวมบริษัท (ก่อนขาย) |      2,300 |         2,300 |

มูลค่ารวมทั้งบริษัท**เท่ากัน** สิ่งที่ต่างคือกำไรของแต่ละสาขา และวิธีโอนสินค้า

**กรณีโอน 5 ชิ้นจาก A ไป B (ก่อนขาย):**

- แยกต่อสาขา: A ตัดออก 5 × 100 = 500 บาท และ B รับเข้าที่ 500 บาท
  ทำให้ B มี 15 ชิ้น มูลค่า 1,300 + 500 = 1,800 บาท ทุนเฉลี่ยของ B จึงเป็น 120 (ส่วนทุนของ A ยังเป็น 100)
- รวมทั้งบริษัท: ย้ายแค่จำนวน ทุนยังเป็น 115 ทั้งสองสาขา

### เปรียบเทียบ

**แยกต่อสาขา (เลือกแล้ว)**

- ✅ บัตรสต็อกแต่ละสาขาครบในตัว (จำนวน / ทุนเฉลี่ย / มูลค่า) ตรวจนับและกระทบยอดกับของจริงในสาขาได้
- ✅ กำไรของสาขาสะท้อนทุนจริงที่สาขานั้นซื้อ ใช้วัดผลงานสาขาได้
- ✅ การรับเข้าที่สาขาหนึ่งไม่เปลี่ยนทุนของบิลที่อีกสาขากำลังขาย
- ✅ สอดคล้องกับรายงานสินค้าและวัตถุดิบของผู้จด VAT ที่ทำแยกตามสถานประกอบการ
- ✅ ใช้ `movingAverage()` / `buildStockCard()` เดิมได้ แค่เพิ่มสาขาเป็นตัวแยก
- ❌ สินค้าตัวเดียวกันมีทุน (และกำไรต่อชิ้น) ต่างกันในแต่ละสาขา
- ❌ ใบโอนต้องบันทึกทุนที่โอนไปด้วย (หัวข้อ 4)

**รวมทั้งบริษัท**

- ✅ ทุกสาขาทุนเท่ากัน การโอนเป็นแค่การย้ายจำนวน
- ❌ ทุนเฉลี่ยในบัตรสต็อกของสาขาเปลี่ยนเองเมื่ออีกสาขารับของ ทั้งที่สาขานี้ไม่มีรายการ ทำให้อ่านและตรวจสอบยาก
- ❌ กำไรของสาขาถูกเฉลี่ยรวมกับสาขาอื่น จึงวัดผลงานสาขาไม่ได้
- ❌ ทุกการรับเข้าต้องล็อกค่าเฉลี่ยชุดเดียวที่ทุกสาขาใช้ร่วมกัน ถ้าสาขามากและขายพร้อมกันจะเป็นคอขวด

### ประเด็นที่ยังให้นักบัญชีตรวจทาน (ไม่เปลี่ยนการตัดสินใจ)

1. ใช้ถัวเฉลี่ยเคลื่อนที่ **แยกตามสาขา (คลัง)** ได้หรือไม่ (ทั้งสองแบบเป็นวิธีถัวเฉลี่ยที่มาตรฐานยอมรับ แต่ต้องใช้วิธีเดิมต่อเนื่อง)
2. รายการโอนระหว่างสาขาใช้ทุนเฉลี่ยของสาขาต้นทาง ณ วันโอน ถูกต้องหรือไม่
3. รายงานสินค้าและวัตถุดิบต้องทำแยกต่อสถานประกอบการตามที่เข้าใจหรือไม่

ตรวจทานให้เสร็จก่อนเริ่มขั้นที่ 3 (สต็อกแยกสาขา)

## 12. รายละเอียด D2 — ราคาและโปรโมชั่นตามสาขา (ยืนยันแล้ว 2026-10-10)

**ตัดสินใจ:**

1. **ราคาขายเดียวทั้งบริษัท** — `SkuPrice` / `currentPrice` เหมือนเดิม ไม่มีราคาเฉพาะสาขาในรอบแรก
2. **โปรโมชั่นจำกัดสาขาได้** — `Promotion.branchIds: number[]` (ว่าง = ทุกสาขา)
3. **โปรเฉพาะสาขาสร้าง/แก้ได้เฉพาะ owner และ admin ระดับบริษัท** (`allBranches`) ผู้จัดการสาขายังไม่ได้

**เหตุผล:** ร้านไอทีมักขายราคาเดียวทั้งเครือ เพราะลูกค้าเทียบราคาข้ามสาขาและกับหน้าเว็บ
งานระบายสต็อกหรือแข่งราคาในพื้นที่ใช้โปรเฉพาะสาขาแทน ซึ่งมีวันเริ่ม-วันจบชัดเจน ดีกว่าแก้ราคาแล้วลืมเปลี่ยนกลับ
กำไรต่อชิ้นยังต่างกันตามสาขาอยู่แล้วจากทุนเฉลี่ยแยกสาขา (D1)

**ตัวอย่าง:** สาขา B มีเมาส์ค้างสต็อก → โปร `item_discount` 10% เฉพาะเมาส์, `branchIds: [B]`
บิลที่สาขา B ได้ส่วนลด ส่วนสาขาอื่นยังขายราคาเต็ม

**กติกา (เพิ่มจากกติกาโปรเดิม):**

- `promotionsForProduct()` / `priceCart()` คัดเฉพาะโปรที่ `branchIds` ว่าง หรือมีสาขาของบิล
  ส่วน priority, stackable, ของแถม และลำดับลดสินค้า → ลดท้ายบิล → ส่วนลดพิเศษ ไม่เปลี่ยน
- server คิดราคาใหม่ใน `POST /sales` ด้วยสาขาจาก `X-Branch-Id` เสมอ (ไม่เชื่อสาขาที่ส่งมาใน payload)
- `promotionError()`: ทุก `branchIds` ต้องเป็นสาขาที่ active ของบริษัท และผู้ใช้ที่ไม่ใช่ owner / admin ระดับบริษัทแก้ไม่ได้
- โปรที่เริ่มแล้ว (`hasStarted()`) ห้ามแก้ `branchIds` (ตามกติกาเดิม: แก้ได้แค่ `enabled`, วันจบที่สั้นลง, `note`)
- ข้อมูลโปรเก่าที่ไม่มี `branchIds` → เติม `[]` ตอนอ่าน (= ทุกสาขา)
- ปิดใช้งานสาขาได้แม้โปรยังอ้างถึงอยู่ (โปรแค่ไม่มีผลที่สาขานั้น)

**ถ้าวันหลังต้องมีราคาเฉพาะสาขา (แบบ B):** เพิ่ม `SkuPrice.branchId: number | null`
(null = ราคากลาง; ช่วงห้ามทับกันภายใน SKU + สาขาเดียวกัน; วันไหนสาขามีราคาเองใช้ราคานั้น ไม่มีใช้ราคากลาง)
ข้อมูลราคาเดิมกลายเป็นราคากลางทันที จึงไม่ต้องย้ายข้อมูล และ POS / ใบเสร็จ / ป้ายราคายังอ่าน `currentPrice` จาก server เหมือนเดิม

## 13. รายละเอียด D3 — คืน / เปลี่ยนสินค้าต่างสาขา (ยืนยันแล้ว 2026-10-10)

**ตัดสินใจ (รอบแรก):**

1. **ใบลดหนี้ (คืนเงิน)** ทำได้เฉพาะสาขาที่ขาย
2. **ใบเปลี่ยนสินค้า** ทำได้เฉพาะสาขาที่ขาย
3. **ยกเลิกบิล (void)** ทำได้เฉพาะสาขาที่ขาย ในวันขาย (กฎตายตัว ไม่เปลี่ยนในอนาคต)

**กติกา:**

- `creditNoteError()` / `exchangeBlocker()` / `exchangeError()` / `voidError()` เพิ่มเงื่อนไข
  `sale.branchId === สาขาปัจจุบัน (X-Branch-Id)` ไม่ตรง → `บิลนี้ขายที่สาขา <ชื่อสาขา> — คืน/เปลี่ยนได้ที่สาขานั้น`
- หน้าบิล (`/sales/:id`) ที่เปิดผ่านมุมมอง "ทุกสาขา" ดูได้ แต่ปุ่มคืน / เปลี่ยน / void ใช้ไม่ได้ พร้อมข้อความข้างบน
- server ตรวจซ้ำทุกครั้ง (ไม่เชื่อหน้าบ้าน)

**ตัวอย่างที่ยังทำไม่ได้ในรอบแรก:** ลูกค้าซื้อเมาส์ที่สาขา A วันจันทร์ (จ่ายบัตร) วันพุธไปขอคืนที่สาขา B
→ พนักงานแจ้งให้กลับไปสาขา A

> **หมายเหตุ — เปิดข้ามสาขาได้ในอนาคต:** ข้อจำกัดนี้เป็นการตัดสินใจทางธุรกิจของรอบแรก ไม่ใช่ข้อจำกัดของโครงสร้างข้อมูล
> ให้ออกแบบตั้งแต่ตอนนี้แบบที่เปิดได้โดยไม่ต้องย้ายข้อมูล:
>
> - เอกสารคืน / เปลี่ยนเก็บ **`branchId` ของตัวเอง** (สาขาที่ทำรายการ) แยกจาก `sale.branchId` (สาขาที่ขาย) ตั้งแต่วันแรก
>   แม้รอบแรกจะเท่ากันเสมอ
> - stock movement ของการคืน / เปลี่ยนลงที่ `branchId` ของเอกสาร ไม่ใช่ของบิล
> - เงื่อนไขสาขาอยู่ในฟังก์ชันกติกาจุดเดียว (`creditNoteError()` / `exchangeBlocker()`) และควบคุมด้วยค่าตั้ง
>   ระดับบริษัท เช่น `CompanyInfo.crossBranchExchange` / `crossBranchReturn` (ค่าเริ่มต้น `false`)
>   ตอนเปิดใช้แค่เปลี่ยนค่าตั้ง + ทำส่วนที่เหลือข้างล่าง

**ลำดับที่แนะนำเมื่อจะเปิดข้ามสาขา:**

1. **ใบเปลี่ยนสินค้าข้ามสาขาก่อน** — ไม่มีเงิน ไม่กระทบภาษี: สาขาที่ทำรายการตัดของใหม่จากคลังตัวเอง
   (กติกา "ของต้องมีในสต็อกก่อน" ใช้สต็อกของสาขานี้) และรับของเก่าเข้าคลังตัวเองที่ทุนตามบรรทัดของบิล
   (Serial: ทุนของเครื่อง) ใบรับประกันยังนับจากวันขาย เลขเอกสารใช้ชุดของสาขาที่ทำรายการ
2. **ใบลดหนี้ข้ามสาขา** — ทำหลังนักบัญชีตอบเรื่องต่อไปนี้:
   - ใบลดหนี้ลงรายงานภาษีขายของสาขาไหน (สาขาที่ออกใบกำกับ หรือสาขาที่รับคืน) และใช้เลขชุดของสาขาไหน
   - คืนเงินได้ทางไหน: เงินสดจากลิ้นชักสาขาที่รับคืน (ยอดเงินสดระหว่างสาขาต้องกระทบกันในรายงาน),
     บัตรเครดิตคืนได้เฉพาะถ้าเครื่องรูดใช้ร้านค้าเดียวกัน, QR / โอน คืนได้ทุกสาขา
   - รายงานยอดขายสุทธิของสาขาแสดงยอดคืนที่สาขาไหน
3. ทั้งสองแบบต้องมี **ช่องค้นหาบิลข้ามสาขาแบบจำกัด** (ค้นด้วยเลขบิล / Serial เพื่อทำรายการคืน / เปลี่ยนเท่านั้น)
   เพราะปกติพนักงานเห็นได้แค่สาขาตัวเอง

## 14. รายละเอียด D4 / D5 — การ login (ยืนยันแล้ว 2026-10-10)

**ตัดสินใจ:**

1. **login = รหัสบริษัท + ชื่อผู้ใช้ + รหัสผ่าน** — `username` ไม่ซ้ำภายในบริษัท (`somchai` มีได้ในหลายบริษัท)
2. **เครื่องจำรหัสบริษัท** — กรอกครั้งแรกครั้งเดียว เก็บใน `StorageService` (`companyCode`, ไม่ล้างตอน logout)
   หน้า login แสดง "บริษัท: ACME (เปลี่ยน)" + ช่องชื่อผู้ใช้ / รหัสผ่าน
3. **subdomain ทำทีหลัง** — `acme.<domain>` แค่เติมรหัสบริษัทให้อัตโนมัติ (ต้องมี DNS wildcard + ใบรับรอง SSL + ค่า deploy)
4. **รีเซ็ตรหัสผ่าน** — พนักงาน: admin ของบริษัทตั้งรหัสใหม่ให้ (หน้าเมนูผู้ใช้งาน) · owner: ลิงก์ทางอีเมล
5. **D5: 1 บัญชี = 1 บริษัท** — คนที่ทำงานให้สองบริษัทมีสองบัญชี

**ทำไมไม่ใช้อีเมลไม่ซ้ำทั้งระบบ (ค่าแนะนำเดิม):** แคชเชียร์ส่วนใหญ่ไม่มีอีเมลงาน → ร้านต้องสร้างอีเมลปลอม
และถ้าเริ่มด้วยอีเมลแล้วจะเปลี่ยนเป็นรหัสบริษัททีหลังต้องเปลี่ยนตัวระบุผู้ใช้ทั้งระบบ ส่วนทางกลับ (เพิ่ม subdomain) ทำได้ง่าย

**กติกา:**

- `email` ไม่บังคับ ยกเว้น role `owner` (ใช้รีเซ็ตรหัสผ่าน / แจ้งเรื่องการเก็บเงิน); ถ้ามีต้องไม่ซ้ำภายในบริษัท
- จำกัดการ login ผิดต่อ (รหัสบริษัท + ชื่อผู้ใช้) และต่อ IP; ข้อความผิดพลาดเหมือนกันทุกกรณี
  ("รหัสบริษัท ชื่อผู้ใช้ หรือรหัสผ่านไม่ถูกต้อง") — ไม่บอกว่ารหัสบริษัทมีอยู่จริง กันการเดารายชื่อลูกค้า
- บริษัทที่ถูกระงับ (ค้างชำระ ฯลฯ) → login ไม่ได้ พร้อมข้อความแจ้ง owner
- platform admin (เจ้าของ SaaS) login ผ่านหน้า / endpoint แยก ไม่ใช้รหัสบริษัท และไม่อยู่ในตาราง user ของ tenant

**หน้าบ้าน (repo นี้):**

- ฟอร์ม login (`AuthLayout`) เพิ่มช่องรหัสบริษัท: ถ้าเครื่องจำไว้แล้วแสดงเป็นข้อความ + ปุ่ม "เปลี่ยน"
- `AuthService.login(companyCode, username, password)`; mock: บริษัทตัวอย่างรหัส `DEMO` (ผู้ใช้ `admin` / `admin`
  และพนักงาน `somchai` / `1234` ตามเดิม)
- เมนูผู้ใช้งาน: ฟิลด์ `username`, อีเมลไม่บังคับ, ปุ่ม "ตั้งรหัสผ่านใหม่" สำหรับ admin

## 15. รายละเอียด D6 — รายงานภาษีขายหลายสาขา (ยืนยันแล้ว 2026-10-10)

พื้นฐาน (ให้นักบัญชียืนยัน): ผู้จด VAT ที่มีหลายสถานประกอบการ ปกติยื่น ภ.พ.30 **แยกทีละสถานประกอบการ**
และทำรายงานภาษีขายแยกทีละสาขา ยื่นรวมที่สำนักงานใหญ่ได้เมื่อ**ได้รับอนุมัติจากกรมสรรพากร**เท่านั้น

**ตัดสินใจ:**

1. **รายงานภาษีขายที่ใช้ยื่น = ทีละสาขาเท่านั้น** (`/sales/tax-report?month=&branchId=`, ต้องเลือกสาขาเสมอ)
   หัวรายงานใช้ชื่อสถานประกอบการ + เลขสาขาของสาขานั้น (`BranchInfo`) ส่วนชื่อผู้ประกอบการ + เลขภาษีจาก `CompanyInfo`
2. **ตารางสรุปภาษีขายทุกสาขา** ต่อเดือน สำหรับ owner / admin ระดับบริษัท
   - แถว = สาขา, คอลัมน์ = มูลค่าสินค้า/บริการ, VAT, ยกเว้นภาษี, รวม + แถวรวมทั้งบริษัท
   - คำนวณจาก `buildSalesTaxReport()` เดิมทีละสาขาแล้วเอา `totals` มาเรียง (ไม่มีสูตรใหม่)
   - ป้ายชัดเจน **"สรุปเพื่อตรวจสอบ — ไม่ใช่รายงานภาษีขายสำหรับยื่น"** ทั้งบนจอ, ตอนพิมพ์ และใน Excel
   - คลิกแถวสาขา → ไปที่รายงานภาษีขายของสาขานั้น
3. **รายงานยื่นรวมฉบับทางการ = ทำทีหลัง** เปิดด้วยค่าตั้ง `CompanyInfo.vatFilingCombined: boolean` (ค่าเริ่มต้น `false`,
   แก้ได้เฉพาะ owner) เมื่อเปิด: หัวรายงานใช้สำนักงานใหญ่ + ระบุ "ยื่นรวม", รายการมีคอลัมน์สาขา, Excel อีกแบบ
   โครงสร้างข้อมูลรองรับอยู่แล้ว เพราะทุกเอกสารมี `branchId`
4. **รายงานภาษีซื้อ = นอกขอบเขต** (ดูข้างล่าง)

**ตัวอย่าง:** สำนักงานใหญ่ (00000) ภาษีขาย ต.ค. 70,000 บาท, สาขา 00001 30,000 บาท
→ รายงานยื่น 2 ฉบับ (ฉบับละสาขา) และตารางสรุปแสดง 2 แถว + รวม 100,000 บาท

**งานในอนาคต — ภาษีซื้อ:** ภ.พ.30 = ภาษีขาย − ภาษีซื้อ แต่ระบบยังไม่บันทึกใบกำกับภาษีซื้อ
(การรับเข้าเก็บแค่ทุนไม่รวม VAT ไม่มีเลขที่ / วันที่ใบกำกับของผู้จำหน่าย) ถ้าจะให้ระบบสรุป ภ.พ.30 ได้ทั้งแบบ ต้องเพิ่ม:
บันทึกใบกำกับภาษีซื้อตอนรับเข้า (เลขที่, วันที่, ผู้จำหน่าย + สาขา, มูลค่า, VAT) แยกตามสาขาที่รับ,
รายงานภาษีซื้อรายเดือนต่อสาขา และการเลื่อนใช้ภาษีซื้อข้ามเดือน (ตามกติกาสรรพากร — ให้นักบัญชีกำหนด)

## 16. รายละเอียด D7 — การแยกข้อมูลระดับฐานข้อมูล (ยืนยันแล้ว 2026-10-10)

เป็นเรื่องของหลังบ้านล้วน: หน้าบ้านไม่เปลี่ยนไม่ว่าเลือกแบบไหน (เห็นแค่ API + token)

**ตัดสินใจ:**

1. **ฐานข้อมูลเดียว ทุกตารางมี `tenant_id` + Row-Level Security (PostgreSQL)** — ถูกที่สุด ดูแลง่าย เหมาะกับร้านเล็ก-กลางจำนวนมาก
2. **เปิดทางย้ายลูกค้าองค์กรไปฐานข้อมูลแยก** (ยังไม่ทำตัวย้าย):
   - ตารางทะเบียนบริษัท (`tenants`) มีฟิลด์บอกฐานข้อมูลที่ใช้ (ค่าเริ่มต้น = ฐานรวม) ทุก request หาฐานจากตรงนี้
   - ย้ายโดยคง id เดิม แล้วตั้ง sequence ของฐานใหม่ให้เริ่มต่อจากค่าสูงสุด → หน้าบ้านยังใช้ `id: number` ได้
3. **export ข้อมูลทั้งบริษัท + ขั้นตอนลบข้อมูลเมื่อเลิกใช้** (PDPA / เลิกใช้บริการ) — ทำในขั้นที่ 6

**ทางเลือกที่ไม่ได้เลือก:** แยก schema ต่อบริษัท / แยกฐานข้อมูลต่อบริษัทตั้งแต่แรก — แยกขาดกว่า กู้ข้อมูลรายบริษัทง่ายกว่า
แต่ค่าใช้จ่ายต่อบริษัทสูง และ migration ต้องรันทุก schema / ทุกฐาน

**สิ่งที่หลังบ้านต้องทำให้ถูก:**

- ตั้ง `SET LOCAL app.tenant_id = …` ภายในแต่ละ transaction (ระวัง connection pool ที่ใช้ connection ซ้ำ — ห้ามใช้ `SET` แบบ session)
- policy ทุกตาราง: `USING (tenant_id = current_setting('app.tenant_id')::bigint)` + `WITH CHECK` แบบเดียวกัน
- แอปต่อฐานด้วย role ที่**ไม่ใช่** superuser / owner ของตาราง และไม่มี `BYPASSRLS`; งาน platform admin ใช้ role แยก
- foreign key แบบรวม `(tenant_id, id)` กันอ้างข้อมูลข้ามบริษัท; index ขึ้นต้นด้วย `tenant_id`
- ตารางใหญ่ (บิลขาย, stock movement) แบ่ง partition ตาม `tenant_id` หรือเดือนเมื่อจำเป็น; รายงานหนักใช้ read replica
  (กันบริษัทใหญ่ทำให้บริษัทอื่นช้า)
- **เทสต์อัตโนมัติ**: ทุก endpoint ยืนยันว่า token ของบริษัท A อ่าน / เขียนข้อมูลบริษัท B ไม่ได้ (รวม id ของอีกบริษัทใน URL / body → 404)
- สำรองข้อมูลแบบ PITR ทั้งฐาน; กู้เฉพาะบริษัท = กู้ทั้งฐานไว้ข้าง ๆ แล้วคัดแถวของ `tenant_id` นั้นกลับ (ทำได้แต่ช้า —
  soft delete + audit log ช่วยลดความจำเป็น)
