# แผนเปิด / ปิดกะ (Shift) + นับเงินตามช่องทางชำระเงิน

สถานะ: **เสร็จ (2026-10-12)** · ขั้นที่ 1–6 ครบ · ข้อตัดสินใจ S1–S6 ยืนยันครบแล้ว (2026-10-11) · `requireShift` อยู่ในรอบแรก · ค้าง: หน้าจอให้ admin ปิดกะของเครื่องอื่น (API ทำได้แล้ว), ตัวกรองเลขกะในหน้ารายการบิล · เลขเครื่องมาจากทะเบียนเครื่อง POS แล้ว (`docs/terminal-plan.md`)

ที่มา: `docs/pos-plan.md` ข้อตัดสินใจ 7 ("เปิด/ปิดกะ + นับเงินลิ้นชัก — รอบถัดไป")
เป้าหมาย: เมื่อแคชเชียร์เปลี่ยนกะ ต้องนับเงินและยอดแต่ละช่องทางชำระเงินของกะนั้นได้ และรู้ว่าเงินขาด/เกินเป็นความรับผิดชอบของใคร

ใช้ของที่มีอยู่: `Sale.payments` (`SalePayment.amount` ของเงินสด = หลังปัดเศษ ไม่รวมเงินทอน), `CreditNote.refunds`,
การคืนเงินตอน void, `opensDrawer()` / `roundCash()` (`payment-method.model.ts`)
หน้ารายการขายสรุปเงินเข้าตามช่องทางได้แล้ว (`summarizeSales()`) แต่เป็นตามช่วงวันที่ ไม่ใช่ตามกะ

## 1. หลักการ

- **กะผูกกับลิ้นชักเงิน (เครื่อง POS) + แคชเชียร์ 1 คน** — 1 เครื่องเปิดได้ทีละ 1 กะ
- **เปลี่ยนแคชเชียร์ = ปิดกะของคนเก่า (นับเงิน) แล้วคนใหม่เปิดกะใหม่** เงินขาด/เกินจึงระบุตัวคนได้
  (หลายคนใช้ลิ้นชักเดียวโดยไม่ปิดกะ → หาคนรับผิดชอบไม่ได้ จึงไม่ทำ)
- **ทุกบิลต้องอยู่ในกะ เมื่อเปิดใช้ระบบกะ** (`StoreInfo.requireShift`, ค่าเริ่มต้น `true`) — POS ขายไม่ได้ถ้าเครื่องนี้ยังไม่เปิดกะ (server ปฏิเสธ 400); void / คืนเงิน / เงินเข้าออกลิ้นชักก็ต้องมีกะ; ร้านที่ปิด `requireShift` ขายได้โดยไม่มีกะ (S6, หัวข้อ 15)
- **เงินเข้าออกนับในกะที่ทำรายการ** ไม่ใช่กะของบิลเดิม (void บิลกะเช้าตอนกะบ่าย → เงินออกจากลิ้นชักกะบ่าย)
- **กะที่ปิดแล้วเปิดใหม่ไม่ได้** แก้ไขด้วยรายการปรับปรุงพร้อมเหตุผล (admin)
- **กะข้ามเที่ยงคืนได้** — กะเป็นของ**วันที่เปิดกะ**; ยอดขาย / ภาษีขายนับตาม**วันที่ของบิล**เสมอ (S5, หัวข้อ 14)
- รองรับ SaaS (`docs/saas-plan.md`): กะมี `branchId` + `terminalId`; เครื่องจำ terminal ไว้ใน `StorageService`
  เหมือนจำรหัสบริษัท (ทะเบียนเครื่อง POS ต่อสาขา — saas-plan หัวข้อ 5)

## 2. วงจรของกะ

1. **เปิดกะ** — นับเงินทอนตั้งต้น (opening float) ด้วยตัวช่วยนับตามชนิดแบงก์ / เหรียญ
   (1000, 500, 100, 50, 20 · 10, 5, 2, 1, 0.50, 0.25) ค่าเริ่มต้น = เงินทอนที่กะก่อนหน้าของเครื่องนี้ทิ้งไว้
2. **ระหว่างกะ** — บันทึก `shiftId` ในทุกรายการที่มีเงินเข้าออก:
   - ขาย (`Sale`), ยกเลิกบิล (void), คืนเงินในใบลดหนี้ (`CreditNote.refunds`)
   - **เงินเข้า / ออกลิ้นชัก** (`CashMovement`: in / out + จำนวน + เหตุผลบังคับ) เช่น เติมเงินทอน, จ่ายค่าส่งของ, นำเงินเข้าตู้เซฟระหว่างกะ
   - เปิดลิ้นชักโดยไม่มีการขาย (log เวลา + ผู้ใช้ + เหตุผล)
   - ใบเปลี่ยนสินค้าไม่มีเงิน ไม่ต้องมีกะ — ถ้าเครื่องมีกะเปิดอยู่จะบันทึก `shiftId` เพื่อนับจำนวนรายการใน Z report
3. **X report** — ยอดสะสม ณ ตอนนั้น ไม่ปิดกะ; ยอดตามช่องทาง / เงินคาดในลิ้นชัก **เฉพาะ admin** แคชเชียร์เห็นแค่จำนวนบิล + ยอดขายรวม (S2)
4. **ปิดกะ (Z report)** — นับแบบไม่เห็นยอดระบบ (หัวข้อ 4) → แสดงยอดคาด / ยอดนับ / ส่วนต่างต่อช่องทาง
   → ใส่เหตุผล / ขออนุมัติถ้าจำเป็น → ระบุเงินนำส่ง + เงินทอนที่ทิ้งไว้ → พิมพ์ใบสรุปปิดกะ 80 มม.

## 3. ยอดที่ระบบคาดต่อช่องทาง (กติกาเดียว ใช้ร่วม UI + mock)

- **เงินสด** = เงินทอนตั้งต้น + Σ `amount` เงินสดของบิลขายในกะ − เงินสดที่คืน (void / ใบลดหนี้) ในกะ
  \+ เงินเข้าลิ้นชัก − เงินออกลิ้นชัก
- **ช่องทางอื่น** = Σ `amount` ของช่องทางนั้นในกะ − ยอดที่คืนผ่านช่องทางนั้นในกะ
- ใช้ `amount` (ไม่ใช่ `tendered`) เพราะเงินทอนออกจากลิ้นชักไปแล้ว และเงินสดถูกปัดเศษแล้ว

**ตัวอย่าง:** เงินทอนตั้งต้น 2,000 · ขายเงินสด 5,350 · บัตร 12,900 · QR 3,500 · คืนเงินสดตามใบลดหนี้ 450 ·
จ่ายค่าส่งของ 200

| ช่องทาง | ยอดคาด                                |            นับได้ | ส่วนต่าง |
| ------- | ------------------------------------- | ----------------: | -------: |
| เงินสด  | 2,000 + 5,350 − 450 − 200 = **6,700** |             6,680 |  **−20** |
| บัตร    | 12,900                                |  12,900 (ยอด EDC) |        0 |
| QR      | 3,500                                 | 3,500 (แอปธนาคาร) |        0 |

→ เงินสดขาด 20 บาท ต้องใส่เหตุผล (ต่ำกว่าเกณฑ์ ไม่ต้องให้ admin อนุมัติ)

## 4. การนับตอนปิดกะ

- **นับแบบไม่เห็นยอดระบบ (blind count)** — กรอกยอดที่นับได้ก่อน ระบบจึงแสดงยอดคาดและส่วนต่าง (กันการปรับตัวเลขให้ตรง) — นับใหม่ได้ 1 ครั้งหลังเห็นส่วนต่าง บันทึกทั้งสองยอด; admin ปิดแทนไม่ต้อง blind (S2, หัวข้อ 11)
- **เงินสด** — นับตามชนิดแบงก์ / เหรียญ ระบบรวมยอด
- **ช่องทางอื่น** — ตามค่าตั้งต่อช่องทาง `PaymentMethod.closeCheck` (ใหม่): `count` กรอกยอดจากหลักฐาน (blind, คิดส่วนต่าง) /
  `confirm` ติ๊ก "ตรวจแล้ว" (บันทึกชื่อ ไม่คิดส่วนต่าง) / `none` ใช้ยอดระบบ — ค่าเริ่มต้น: บัตร / ผ่อน / QR = `count`,
  โอน / e-wallet / อื่น ๆ = `confirm`; เงินสด = `count` เสมอ; ยอดเต็มไม่หักค่าธรรมเนียม (S4, หัวข้อ 13)
- **ส่วนต่าง ≠ 0 ต้องมีเหตุผล** (หมวด + รายละเอียด) ทีละช่องทาง; ช่องทางใด |ส่วนต่าง| เกิน `StoreInfo.shiftVarianceLimit` (ใหม่ใน Settings, ค่าเริ่มต้น 100 บาท)
  → ต้องให้ admin อนุมัติ (ใส่รหัสผ่าน admin ที่เครื่องทันที หรือปิดเป็น "รออนุมัติ" แล้ว admin อนุมัติภายหลัง) (S3, หัวข้อ 12)
- **เงินนำส่ง** — ยอดเงินสดที่นำส่ง (เข้าเซฟ / ธนาคาร) + เงินทอนที่ทิ้งไว้ในลิ้นชัก = ยอดนับเงินสด
  เงินทอนที่ทิ้งไว้เป็นค่าเริ่มต้นของการเปิดกะถัดไปของเครื่องนี้

## 5. ข้อมูล

```ts
// core/models/shift.model.ts (ร่าง)
type ShiftStatus = 'open' | 'closed';
type VarianceReason = 'wrong_change' | 'wrong_received' | 'wrong_method' | 'unknown' | 'other';
type CloseCheck = 'count' | 'confirm' | 'none'; // อยู่ใน payment-method.model.ts (S4)

interface Shift {
  id: number;
  shiftNo: string; // 'SH-<วันเปิดกะ YYYYMMDD>-NN' (SaaS: 'SH-<สาขา>-YYYYMMDD-NN'), server ออก
  terminalId: number; // (+ branchId เมื่อทำ SaaS)
  cashier: string; // ผู้เปิดกะ = ผู้รับผิดชอบ
  status: ShiftStatus;
  openedAt: string;
  openingFloat: number;
  openingDenominations: DenominationCount[];
  closedAt: string | null;
  counts: ShiftCount[]; // ต่อช่องทาง ตอนปิด
  cashDenominations: DenominationCount[];
  depositAmount: number; // เงินนำส่ง
  floatLeft: number; // เงินทอนที่ทิ้งไว้
  approvalStatus: 'not_needed' | 'pending' | 'approved'; // S3
  approvedBy: string | null;
  approvedAt: string | null;
  closedBy: string | null; // = cashier ปกติ; admin เมื่อปิดแทน (หมายเหตุ "ปิดแทน" ใน note)
  note: string;
}

interface ShiftCount {
  methodId: number;
  name: string; // snapshot
  expected: number; // server คำนวณตอนปิด (snapshot)
  counted: number | null; // ยอดสุดท้าย; null = closeCheck 'confirm' / 'none' (ไม่คิดส่วนต่าง)
  closeCheck: CloseCheck; // snapshot ค่าตั้งตอนปิด
  confirmedBy: string | null; // คนติ๊ก "ตรวจแล้ว" (confirm)
  firstCount: number | null; // ยอดนับครั้งแรก ถ้ามีการนับใหม่ (S2)
  reasonCode: VarianceReason | null; // ต้องมีเมื่อส่วนต่าง ≠ 0 (S3)
  reason: string;
}

interface CashMovement {
  id: number;
  shiftId: number;
  type: 'in' | 'out';
  amount: number;
  reason: string;
  by: string;
  at: string;
}
```

  และ `CashMovement`; แสดงทุกช่องทางที่ active + ช่องทางที่ปิดใช้แต่มียอดในกะ · `drawerExpected()`

- ฟิลด์ใหม่ในโมเดลเดิม (optional / เติมตอนอ่าน — ข้อมูลเก่าใช้ได้):

## 6. API (เพิ่มใน mock ด้วย)

- เครื่อง POS = header **`X-Terminal-Id`** (ไม่มี / ไม่ถูกต้อง = 1); POS เริ่มส่งในขั้นที่ 3
- `GET /shifts/current` (ของเครื่องนี้) → `Shift | null`
- `POST /shifts/open { terminalId, openingFloat, openingDenominations }` (เครื่องนี้มีกะเปิดอยู่แล้ว → 400)
- `POST /shifts/:id/cash-movements { type, amount, reason }` (`cashMovementError()`; เงินออกเกินเงินสดคาด → 400)
- `GET /shifts/:id/summary` → X report (กะเปิด) / Z report (กะปิด); ผู้ใช้ไม่ใช่ admin ขณะกะเปิด → ได้แค่จำนวนบิล + ยอดขายรวม (ไม่มียอดตามช่องทาง / ยอดคาด)
- `POST /shifts/:id/count-check { counts }` → `CountCheckResult` (ยอดคาด / ส่วนต่างต่อช่องทาง + `needsApproval`) — เปิดเผยเฉพาะหลังกรอกยอดครบ (`countInputsError()` → 400), ไม่บันทึกอะไร; **backend จริงควรบันทึก count-check ครั้งแรกเอง** แทนการเชื่อ `firstCount` จาก client
- `POST /shifts/:id/close { counts (+ เหตุผลต่อช่องทาง), cashDenominations, depositAmount, note, approval: { username, password } | null }` (`closeShiftError()` → 400) — ผู้อนุมัติ = admin ที่ปิดกะเอง หรือ admin ที่ใส่ username / password ที่เครื่อง (server ตรวจ; ผิด / ไม่ใช่ admin → 400) ไม่อย่างนั้นส่วนต่างเกินเกณฑ์ได้ `pending`
- `POST /auth/verify { username, password }` → `{ user }` ตรวจรหัสผ่านโดยไม่เปลี่ยน session (ปลดล็อกหน้าจอ); ผิด → **400** (ไม่ใช่ 401 ที่ทำให้ logout)
- `POST /shifts/:id/approve { note }` (admin; กะ `pending` → `approved`)
- `GET /shifts/variance-report?from&to` → ส่วนต่างต่อแคชเชียร์ (S3)
- `GET /shifts[?from&to]` (กรองตาม**วันที่เปิดกะ**; `?openOnly=1` = กะที่ยังเปิด), `GET /shifts/:id`, `GET /shifts/:id/movements` (เงินเข้า / ออกของกะ)
- `POST /sales`, `POST /sales/:id/void`, `POST /sales/:id/credit-notes` (คืนเงินทุกช่องทาง) → `requireShift` เปิดอยู่ + เครื่องนี้ไม่มีกะเปิด → 400; ขายโดยผู้ใช้ที่ไม่ใช่เจ้าของกะ → 400 (void / คืนเงินโดย admin ได้)

## 7. หน้าจอ

- **POS (`/pos`)**
  - แถบบนแสดงสถานะกะ: เลขกะ, แคชเชียร์, เวลาเปิด (เปิดนานเกิน `shiftMaxHours` → สีเตือน); ไม่มีกะ → dialog เปิดกะแทนตะกร้า
  - เมนูกะ: นำเงินเข้า / ออก, เปิดลิ้นชัก, X report, ปิดกะ
  - คนที่ login ไม่ใช่เจ้าของกะ → ขายไม่ได้ (admin ทำ void / คืนเงินได้) ต้องให้เจ้าของกะปิดกะก่อน หรือ admin ปิดแทน (S1)
  - ปุ่ม **พักหน้าจอ** — ล็อกทั้งแอปจนกว่าเจ้าของกะหรือ admin ใส่รหัสผ่าน (`auth/verify`); สถานะล็อกเก็บใน localStorage `pos.locked` จึงยังล็อกหลัง reload
- **ปิดกะ (`/pos/shift-close`)** — นับ blind count → ผลส่วนต่าง → เหตุผล / อนุมัติ → พิมพ์ Z report (80 มม., `printElement()`)
- **เมนูการขาย** — `/sales/shifts` รายการกะ (สถานะ, แคชเชียร์, ยอดขาย, ส่วนต่าง, ผู้อนุมัติ; กรองช่วงวันตาม `date-range.ts`;
  ตัวกรอง "รออนุมัติ" + ปุ่มอนุมัติ; แท็บรายงานส่วนต่างต่อแคชเชียร์)
  และ `/sales/shifts/:id` รายละเอียด + บิลในกะ + พิมพ์ซ้ำ; รายการบิลแสดง / กรองเลขกะได้
- **Settings** — `requireShift` (ใช้ระบบกะ, ค่าเริ่มต้นเปิด), `shiftVarianceLimit`, `shiftMaxHours` (ค่าเริ่มต้น 12); ช่องทางชำระเงิน — `closeCheck`

## 10. รายละเอียด S1 — กะเป็นของใคร (ยืนยันแล้ว 2026-10-11)

**ตัดสินใจ:** 1 กะ = 1 เครื่อง POS (ลิ้นชัก) + แคชเชียร์ 1 คน — ความรับผิดชอบเงินขาด / เกินชัดเจน
(ร้านไอที: แคชเชียร์ 1–2 คนต่อสาขา บิลไม่มากแต่มูลค่าสูง)

**กติกา:**

1. **คนที่เปิดกะเท่านั้นที่ขายในกะนั้นได้**
2. **1 คนมีกะเปิดได้ทีละ 1 กะ** (เปิดกะ 2 เครื่องพร้อมกันไม่ได้) และ 1 เครื่องมีกะเปิดได้ทีละ 1 กะ
3. **พักสั้น → "พักหน้าจอ"** ล็อก POS จนกว่าเจ้าของกะใส่รหัสผ่าน; ระหว่างนั้นไม่มีใครขายในกะนี้ได้
   ถ้าต้องมีคนขายแทน → ปิดกะ แล้วอีกคนเปิดกะใหม่
4. **ลืมปิดกะ → admin ปิดแทนได้** (นับพร้อมพยาน) บันทึก `closedBy` = admin + หมายเหตุ "ปิดแทน";
   เงินขาด / เกินยังนับเป็นของเจ้าของกะ
5. **admin ทำ void / คืนเงิน (ใบลดหนี้) ในกะของคนอื่นที่เครื่องนั้นได้** — เงินเข้าออกลิ้นชักของกะนั้น
   และบันทึกชื่อ admin เป็นผู้ทำรายการ; **แต่ admin ขายในกะของคนอื่นไม่ได้** (ต้องเปิดกะของตัวเองที่เครื่องอื่น)
6. **คืนเงินทุกช่องทางต้องทำที่เครื่องที่มีกะเปิด** รวมถึงหน้าใบลดหนี้ `/sales/:id/credit-note`
   (เงินสดต้องออกจากลิ้นชักหนึ่ง และยอดคืนของช่องทางอื่นต้องเข้ายอดปิดกะ) — เครื่องไม่มีกะ → บล็อกการคืนเงิน

**ขยายในอนาคต:** ร้านที่เจ้าของขายเองอาจอยากได้ "1 ลิ้นชัก หลายคนใช้ร่วม" (ไม่ต้องปิดกะตอนเปลี่ยนคน)
→ ทำเป็นค่าตั้งระดับบริษัท / สาขาได้โดยไม่เปลี่ยนโครงสร้าง เพราะบิลบันทึกชื่อคนขาย (`Sale.cashier`) อยู่แล้ว

## 11. รายละเอียด S2 — นับแบบไม่เห็นยอดระบบ (ยืนยันแล้ว 2026-10-11)

**ตัดสินใจ:**

1. **ทุกช่องทางที่ต้องนับใช้ blind count** — แคชเชียร์กรอกยอดที่นับได้ (เงินสดตามชนิดแบงก์ / เหรียญ, บัตรจากสลิปสรุป EDC)
   ก่อน แล้วระบบจึงแสดงยอดคาดและส่วนต่าง
2. **นับใหม่ได้ 1 ครั้ง** หลังเห็นส่วนต่าง — บันทึกทั้งยอดครั้งแรก (`firstCount`) และยอดสุดท้าย (`counted`);
   Z report แสดงทั้งสองยอดเมื่อไม่เท่ากัน; แก้ตัวเลขเงียบ ๆ ไม่ได้
3. **X report ระหว่างกะ** — ยอดตามช่องทางและเงินคาดในลิ้นชักเห็นได้**เฉพาะ admin**;
   แคชเชียร์เห็นแค่จำนวนบิล + ยอดขายรวมของกะ (คำนวณเงินในลิ้นชักแม่นยำไม่ได้ เพราะมีเงินทอนตั้งต้น / คืนเงิน / เงินเข้าออก)
   — server ตัดข้อมูลตาม role ไม่ใช่แค่ซ่อนในหน้าจอ
4. **admin ปิดกะแทน (S1)** ไม่ต้อง blind (admin เห็นยอดระบบได้อยู่แล้ว) แต่บันทึกว่าเป็นการปิดแทน

**เหตุผล:** ถ้าเห็นยอดระบบระหว่างนับ เงินขาดอาจถูกเติมเงียบ ๆ และเงินเกินอาจถูกหยิบออก จนผู้จัดการไม่เห็นปัญหา
(เงินเกินมักแปลว่าทอนลูกค้าขาด หรือมีการขายที่ไม่ผ่านระบบ) ตัวเลขจริงทำให้เห็นรูปแบบเงินขาด / เกินของแต่ละคน
และปกป้องแคชเชียร์จากข้อสงสัยว่าแต่งตัวเลข

**ตัวอย่าง:** ยอดคาดเงินสด 6,700 · นับครั้งแรก 6,680 → ขาด 20 · นับใหม่ได้ 6,700 → ส่วนต่าง 0
→ Z report แสดง "นับครั้งแรก 6,680 / นับใหม่ 6,700"

## 12. รายละเอียด S3 — เกณฑ์ส่วนต่างและการอนุมัติ (ยืนยันแล้ว 2026-10-11)

**ตัดสินใจ:**

1. **เกณฑ์ดูรายช่องทาง เป็นบาทคงที่** — `StoreInfo.shiftVarianceLimit` (Settings, ค่าเริ่มต้น 100 บาท;
   SaaS: ค่าตั้งระดับสาขา) ช่องทางใด |ส่วนต่าง| > เกณฑ์ → ต้องอนุมัติ
   - ไม่ใช้ยอดรวม: เงินสดขาด 500 + บัตรเกิน 500 = รวม 0 แต่มีปัญหาสองจุด
   - ไม่ใช้ % ของยอดขาย: วันขายดี เงินหายหลายร้อยก็ไม่ถึงเกณฑ์
2. **ส่วนต่าง ≠ 0 ต้องมีเหตุผลทุกครั้ง** ต่อช่องทาง: หมวด (`VarianceReason`) + รายละเอียด
   - หมวด: ทอนเงินผิด (`wrong_change`) / รับเงินผิด (`wrong_received`) / กดช่องทางชำระผิด (`wrong_method`, เช่น ลูกค้าจ่าย QR แต่กดเงินสด) /
     ไม่ทราบสาเหตุ (`unknown`) / อื่น ๆ (`other`, ต้องพิมพ์รายละเอียด)
   - การปัดเศษเงินสดอยู่ในยอดคาดแล้ว ไม่ใช่ส่วนต่าง
3. **อนุมัติได้ 2 ทาง** — `approvalStatus`: `not_needed` / `pending` / `approved`
   - ทันที: admin ใส่รหัสผ่านที่เครื่อง → ปิดเป็น `approved`
   - ภายหลัง: ปิดเป็น `pending` → admin อนุมัติจาก `/sales/shifts` (`POST /shifts/:id/approve`)
   - กะ `pending` **ไม่บล็อก**การเปิดกะถัดไป (ร้านต้องขายต่อได้) แต่หน้ารายการกะ + แดชบอร์ดแสดงจำนวนที่ค้างอนุมัติ
4. **รายงานส่วนต่างต่อแคชเชียร์ตามช่วงเวลา** — จำนวนกะ, จำนวนครั้งที่ขาด / เกิน, ยอดรวมขาด / เกิน ต่อช่องทาง
   (จับรูปแบบที่ขาดทีละน้อยต่ำกว่าเกณฑ์ เช่น 50 บาททุกวัน = 1,500 บาท / เดือน)
5. **ระบบแค่บันทึก** — ไม่แก้บิล / ยอดขาย / ภาษีขายเพื่อให้ยอดตรง (ส่วนต่างทางบัญชี = เงินสดขาด / เกิน
   นักบัญชีกำหนดบัญชีที่ใช้) และไม่คำนวณการหักเงินพนักงาน (นโยบายฝ่ายบุคคล ต้องเป็นไปตามกฎหมายคุ้มครองแรงงาน)

**ตัวอย่าง (เกณฑ์ 100 บาท):**

| เงินสด  | บัตร    | ผล                                                                   |
| ------- | ------- | -------------------------------------------------------------------- |
| ต่าง 0  | ต่าง 0  | ปิดได้ทันที (`not_needed`)                                           |
| ขาด 20  | ต่าง 0  | ใส่เหตุผล แล้วปิดได้ (`not_needed`)                                  |
| ขาด 150 | ต่าง 0  | ใส่เหตุผล + admin อนุมัติ (ทันที → `approved` / ภายหลัง → `pending`) |
| ขาด 80  | เกิน 80 | ใส่เหตุผลทั้งสองช่องทาง แล้วปิดได้ (แต่ละช่องทางไม่เกิน 100)         |

## 13. รายละเอียด S4 — ตรวจช่องทางที่ไม่ใช่เงินสดตอนปิดกะ (ยืนยันแล้ว 2026-10-11)

**ทำไมต้องตรวจ:** บัตรถูกปฏิเสธที่ EDC แต่ POS บันทึกขายแล้ว (ร้านเสียเงินเต็มจำนวน) · สลิป PromptPay ปลอม ·
กดช่องทางผิด (จ่าย QR แต่กดเงินสด → เงินสดขาด / QR เกินพอดีกัน — หมวดเหตุผล `wrong_method`)

**ตัดสินใจ:**

1. **ค่าตั้งต่อช่องทาง `PaymentMethod.closeCheck` 3 ระดับ** (แก้ในหน้าช่องทางชำระเงิน; `withPaymentTypeRules()` บังคับเงินสด = `count`):

   | ระดับ     | ตอนปิดกะ                                                  |
   | --------- | --------------------------------------------------------- |
   | `count`   | กรอกยอดจากหลักฐาน แบบ blind (S2) คิดส่วนต่างตามเกณฑ์ (S3) |
   | `confirm` | ติ๊ก "ตรวจแล้ว" บันทึกชื่อ ไม่คิดส่วนต่าง                 |
   | `none`    | ใช้ยอดระบบ ไม่ต้องทำอะไร                                  |

2. **ค่าเริ่มต้นตามประเภท** (ข้อมูลเก่าที่ไม่มีค่า → เติมตอนอ่าน):

   | ประเภท                  | ค่าเริ่มต้น             | หลักฐาน                                   |
   | ----------------------- | ----------------------- | ----------------------------------------- |
   | เงินสด                  | `count` (เปลี่ยนไม่ได้) | นับแบงก์ / เหรียญ                         |
   | บัตร                    | `count`                 | สลิปสรุปยอด EDC (settlement)              |
   | ผ่อน                    | `count`                 | สลิป EDC (ผ่อนผ่านบัตร)                   |
   | QR (PromptPay)          | `count`                 | ยอดของวันในแอปร้านค้าธนาคาร (จับสลิปปลอม) |
   | โอน / e-wallet / อื่น ๆ | `confirm`               | ตรวจทีละรายการในแอปธนาคาร                 |

3. **กรอกยอดเต็ม (gross)** ไม่หักค่าธรรมเนียม — ยอดรับสุทธิหลัง MDR ดูจาก `netReceived()` ในรายงาน (คนละเรื่องกับการนับกะ)
4. **กระทบยอดธนาคาร / EDC รายวัน = งานในอนาคต** (นอกขอบเขตรอบนี้)

**ข้อแนะนำการตั้งค่า:**

- 1 ลิ้นชักมี EDC ของตัวเอง → ปิดยอด EDC (settlement) ทุกครั้งที่ปิดกะ แล้วกรอกยอดจากสลิป
- EDC เครื่องเดียวใช้ร่วมหลายลิ้นชัก → สลิปรวมยอดหลายกะ เทียบรายกะไม่ได้ → ตั้งบัตรเป็น `confirm` และตรวจยอดรวมตอนสิ้นวัน
- แคชเชียร์เปิดแอปธนาคารไม่ได้ (บัญชีของเจ้าของ) → ตั้ง QR เป็น `none` แล้ว admin กระทบยอดธนาคารรายวันเอง

## 14. รายละเอียด S5 — กะข้ามเที่ยงคืน (ยืนยันแล้ว 2026-10-11)

**ตัดสินใจ:**

1. **กะข้ามเที่ยงคืนได้** — ไม่บังคับปิดตอนเที่ยงคืน (ระบบนับเงินแทนคนไม่ได้ และไม่ขัดจังหวะลูกค้าที่ค้างอยู่)
2. **กะเป็นของวันที่เปิดกะ** — เลขกะ, การกรองรายการกะ และยอดเงินนำส่งรายวันใช้วันเปิดกะ;
   **ยอดขาย / ภาษีขายนับตามวันที่ของบิลเสมอ** (ใบกำกับต้องลงวันที่ที่ขายจริง, เลขบิล `POS-YYYYMMDD` รันตามวันปฏิทิน)
3. **เตือนเมื่อกะเปิดนาน** — เกิน `StoreInfo.shiftMaxHours` (Settings, ค่าเริ่มต้น 12 ชั่วโมง): แถบสถานะกะใน POS เป็นสีเตือน
   และหน้ารายการกะ / แดชบอร์ดของ admin แสดง "กะเปิดค้าง" — **เตือนอย่างเดียว ไม่บล็อกการขาย** (ลืมปิด → admin ปิดแทนตาม S1)
4. **ไม่มีระบบตัดรอบ "วันทำการ"** (เช่น ตี 4) — ขัดกับวันที่บนใบกำกับภาษีและเลขบิลรายวัน

**ตัวอย่าง:** กะ `SH-20261010-02` เปิด 16:00 วันที่ 10 ต.ค. ปิด 00:30 วันที่ 11 ต.ค.

| บิล | เวลา            | เลขบิล              | รายงานขาย / ภาษีขาย |
| --- | --------------- | ------------------- | ------------------- |
| 1   | 23:40 วันที่ 10 | `POS-20261010-0045` | วันที่ 10           |
| 2   | 00:15 วันที่ 11 | `POS-20261011-0001` | วันที่ 11           |

- Z report ของกะรวมทั้งสองบิล; กะนี้อยู่ในรายการกะของวันที่ 10
- ยอดขายรายวันกับยอดเงินของกะในวันนั้นจึงต่างกันเล็กน้อยในวันที่มีกะข้ามเที่ยงคืน — ปกติ;
  หน้ารายละเอียดกะแสดงบิลพร้อมวันที่ให้ตรวจย้อน
- ข้ามสิ้นเดือน (คืน 31 ต.ค.) → บิลหลังเที่ยงคืนเข้ารายงานภาษีขายของ**พฤศจิกายน**
- กฎเดิม: void ได้เฉพาะในวันขาย → บิล 1 (23:40) ถ้ายกเลิกตอน 00:10 ต้องออกใบลดหนี้แทน

## 15. รายละเอียด S6 — ขายโดยไม่เปิดกะ (ยืนยันแล้ว 2026-10-11)

**ตัดสินใจ:** ทุกบิลขายต้องอยู่ในกะ — POS ไม่มีกะ → แสดง dialog เปิดกะ; server ตรวจเอง (`POST /sales` จากเครื่องที่ไม่มีกะเปิด → 400)
ไม่ใช่แค่ซ่อนปุ่มในหน้าจอ

**เหตุผล:** บิลนอกกะทำให้การนับเงิน (S1–S5) เชื่อถือไม่ได้ทันที — เช่น ขายเงินสด 5,000 นอกกะ เงินอยู่ในลิ้นชักแต่ไม่อยู่ในยอดคาดของกะไหน
กะถัดไปจะดูเหมือนเงินเกิน; การเปิดกะอัตโนมัติตอนบิลแรก (เงินทอนตั้งต้น 0) ก็ทำให้ยอดเงินสดคาดผิดตั้งแต่ต้น

| รายการ                          | ต้องมีกะ | หมายเหตุ                                                                 |
| ------------------------------- | -------- | ------------------------------------------------------------------------ |
| ขาย (POS)                       | ✅       | เงินเข้า                                                                 |
| ยกเลิกบิล / คืนเงินในใบลดหนี้   | ✅       | เงินออก (S1 ข้อ 6)                                                       |
| นำเงินเข้า / ออกลิ้นชัก         | ✅       |                                                                          |
| ใบเปลี่ยนสินค้า                 | ❌       | ไม่มีเงิน; ถ้าเครื่องมีกะเปิดอยู่ บันทึก `shiftId` (นับจำนวนใน Z report) |
| ใบกำกับภาษีเต็มรูปที่ออกภายหลัง | ❌       | เอกสาร ไม่มีเงิน                                                         |
| พักบิล / เรียกบิลกลับ           | ❌       | ยังไม่รับเงิน — ตอนชำระเงินต้องมีกะ                                      |

**การเริ่มใช้:**

- บิลก่อนเปิดใช้ระบบกะไม่มี `shiftId` — **ไม่ย้อนใส่**; รายงานขายรายวันใช้ได้ตามเดิม รายงานกะเริ่มตั้งแต่วันเปิดใช้
  (`shiftId` เป็น optional ในโมเดล — ข้อมูลเก่าเติม `null` ตอนอ่าน)
- วันแรกทุกเครื่องต้องเปิดกะก่อนขาย — แจ้งร้านล่วงหน้า

**ค่าตั้ง `StoreInfo.requireShift` — ใช้ระบบกะหรือไม่ (ย้ายเข้ารอบแรก 2026-10-11):** สำหรับร้านเล็กที่เจ้าของขายเองคนเดียว

|                 | `true` (ค่าเริ่มต้น)       | `false`                                                 |
| --------------- | -------------------------- | ------------------------------------------------------- |
| POS             | ต้องเปิดกะก่อนขาย          | ขายได้เลย ไม่มีแถบสถานะกะ / dialog เปิดกะ / เมนูกะ      |
| นับเงิน / ปิดกะ | ตาม S1–S5                  | ไม่มี                                                   |
| void / คืนเงิน  | ต้องมีกะ                   | ทำได้เลย                                                |
| บิล / ใบลดหนี้  | มี `shiftId`               | `shiftId = null`                                        |
| รายงาน          | รายงานกะ + รายงานขายรายวัน | รายงานขายรายวัน (สรุปเงินเข้าตามช่องทาง) เหมือนปัจจุบัน |

- แก้ได้เฉพาะ admin ในหน้า Settings (SaaS: owner / admin ระดับบริษัท ตั้งได้ทั้งบริษัทหรือรายสาขา)
- **เปิด → ปิด:** ต้องปิดกะที่ค้างอยู่ทุกเครื่องก่อน — ยังมีกะเปิด → `storeInfoError()` / 400 ("ยังมีกะที่เปิดอยู่ N กะ")
- **ปิด → เปิด:** บิลก่อนหน้าที่ไม่มีกะไม่ต้องย้อนใส่ (เหมือนวันเริ่มใช้); เครื่องต้องเปิดกะก่อนขายบิลถัดไป
- เมนู `/sales/shifts` ยังเปิดดูกะเก่าได้แม้ปิด `requireShift` อยู่
- server เป็นคนตรวจ (`POST /sales` / void / คืนเงิน อ่านค่าตั้งตอนนั้น) ไม่ใช่แค่ซ่อนในหน้าจอ
- ข้อมูลเก่าที่ไม่มีค่า → เติม `true` ตอนอ่าน (`STORE_INFO_DEFAULTS`)
