# แผนทดสอบหน้าจอก่อนเริ่ม SaaS

สถานะ: **R1–R2 รันแล้ว** (2026-10-13, Claude in Chrome) · R3–R7 ยังไม่ได้รัน

## เป้าหมาย

ก่อนเริ่มงาน SaaS (`docs/saas-plan.md`) ต้องยืนยันว่า**ทุกหน้าจอที่มีอยู่ทำงานตามกฎ**ใน `CLAUDE.md` และ `docs/*-plan.md`
เพื่อให้แยกได้ว่าบั๊กที่เจอหลังทำ SaaS เกิดจากการเปลี่ยน tenant / สาขา ไม่ใช่บั๊กเดิม

วิธีทดสอบ: **คลิกผ่านหน้าจอจริง** (Claude in Chrome หรือคน) บน `npm start` แล้วกรอกผลลงคอลัมน์ "ผล"
ผลรอบเปิดกะที่ทำแล้วอยู่ใน `docs/test-plan.md` ข้อ 1 — ไม่ทำซ้ำในเอกสารนี้

ผล: ✅ ผ่าน · ❌ ไม่ผ่าน · ⚠️ ผ่านแต่มีข้อสังเกต · ⏭️ ทดสอบผ่านหน้าจอไม่ได้ / ข้าม (ระบุเหตุผล)

## ข้อจำกัดและวิธีทำงานกับ mock

- **ยังไม่ต่อ API จริง** — ทุก request ตอบโดย `mock-backend.interceptor.ts` ข้อมูลอยู่ใน localStorage `an22.mock.db`
  (ลบ key = กลับเป็น seed) กฎฝั่ง server จึงทดสอบได้เท่าที่หน้าจอยิงถึง
  กรณีที่หน้าจอกันไว้ก่อนจนยิงไม่ถึง → ⏭️ และอ้าง unit test ใน `mock-backend.interceptor.spec.ts`
- **วันที่ = นาฬิกาเครื่อง** — seed ไม่มีบิล POS ของวันก่อน กรณีที่ต้องการบิล "เมื่อวาน" (ใบลดหนี้, void ข้ามวัน, ระยะเปลี่ยนสินค้า)
  ให้ขายบิลใหม่แล้วแก้ `date` ของบิลนั้นใน `an22.mock.db` ย้อนไป 1 วัน (หรือมากกว่า) ผ่าน DevTools — บันทึกไว้ในขั้นตอนว่าทำแบบนี้
- **หลายเครื่อง** — ใช้เบราว์เซอร์เดียว ตั้ง `an22.pos.terminal` ใน localStorage เป็นเลขเครื่องที่ต้องการแล้ว reload
  (หน้าตั้งค่าล็อกเลขเครื่องไว้ระหว่างที่มีกะเปิด)
- **การพิมพ์** — ไม่กดปุ่มที่เปิด print dialog ของเบราว์เซอร์ระหว่างทดสอบอัตโนมัติ (บล็อกการคุมเบราว์เซอร์) ตรวจจากตัวอย่างบนหน้าจอ / สำเนาในหน้าบิลแทน
  ส่วนที่ต้องดูผลพิมพ์จริง (ขนาด 80 มม. / A4 / ฉลาก) ให้คนกดพิมพ์เป็น PDF เอง
- **นอกขอบเขต**: API จริง, performance, เบราว์เซอร์อื่น, เครื่องพิมพ์จริง, ลิ้นชักเงินจริง
- **Claude in Chrome (จาก R1)** — คลิกบางครั้งไม่ถึง element (ปุ่มไอคอนในตาราง, เปิด `mat-select`) โดยเฉพาะหลัง `scroll_to`
  ไม่ใช่บั๊กของแอป (กดซ้ำ / คลิกตามพิกัดที่คำนวณจาก `getBoundingClientRect()` / `MatSelect.open()` ผ่าน `ng.getComponent` ได้ผล);
  ย่อหน้าต่างไม่ได้เมื่อ Chrome ขยายเต็มจอ — กรณีจอแคบให้คนทดสอบ

### เตรียมก่อนเริ่ม

1. `npm start` → http://localhost:4200
2. DevTools → ลบ localStorage `an22.mock.db`, `an22.pos.terminal`, `an22.pos.locked` → reload
3. login `admin / admin` → ตั้งค่า → เครื่องนี้ = เครื่อง 1

### ลำดับรอบ

ทำตามลำดับเพราะข้อมูลต่อกัน (เช่น SKU ที่สร้างใน R2 ใช้ขายใน R4):
**R1** auth / ผู้ใช้ / ข้อมูลหลัก (หัวข้อ 1–3) → **R2** SKU / ราคา / โปร (4–6) → **R3** คลัง (7) → **R4** POS + กะ (8–9)
→ **R5** หลังการขาย (10) → **R6** ตั้งค่า / แดชบอร์ด (11–12) → **R7** ข้ามเมนู / สิทธิ์ (13)

## จุดที่ต้องจดไว้สำหรับ SaaS

ไม่ต้องทดสอบตอนนี้ — จดเพิ่มเมื่อเจอระหว่างรัน เพื่อใช้ตอนทำ `docs/saas-plan.md`

- ข้อมูลที่ตอนนี้เป็นระดับ "ร้านเดียว": `StoreInfo` (ชื่อ / tax ID / สาขา / ค่าตั้งค่ากะ / ส่วนลด), ทะเบียนเครื่อง POS (ต่อร้าน → ต่อสาขา)
- เลขเอกสารที่รันทั้งร้าน: `INV-`, `CN-`, `EX-`, `SH-` — ต้องตัดสินใจว่าต่อบริษัทหรือต่อสาขา
- ค่าใน localStorage ที่ผูกกับเครื่อง (`pos.terminal`, `pos.locked`) — ต้องรู้สาขาด้วย
- สิทธิ์: ตอนนี้มีแค่ admin / staff (ผลจาก 2.6, 3.25, 11.3, 11.8, 13.1)
  - R1: staff ทำได้ทุกอย่างที่ `/users` (B2) และเพิ่ม / แก้ / ลบ หมวดหมู่ ผู้จำหน่าย ช่องทางชำระเงินได้ (ไม่มีการเช็กสิทธิ์ทั้งหน้าจอและ mock);
    เครื่อง POS เป็นแท็บเดียวที่ staff ดูได้อย่างเดียว (หน้าจอซ่อนปุ่ม + mock ตอบ 403)
- ข้อมูลที่ R1 สร้างไว้ใช้ต่อ: หมวด `TS` > `TS-A` > `TS-A-1` (ปิดใช้งาน — ใช้ใน 3.4 / 3.6), ผู้จำหน่าย `SUP-T1` (taxId SUP-CPS สาขา 00002, เครดิต 30),
  ลำดับปุ่มชำระ TMW อยู่ก่อน TRANSFER, เครื่องนี้ = เครื่อง 1
- ข้อมูลที่ R2 สร้างไว้ใช้ต่อ: หมวด `TS-B` (ระดับ 2) และ `TS-A-1` เปิดใช้งานแล้ว; SKU `TST-001` (ปกติ, TS-B, barcode 2000000000015, แพ็ค ×10 = 2000000000022,
  ผู้จำหน่าย SUP-ITD + SUP-T1 (main), จุดสั่งซื้อ 5, ราคา ฿500 ถึง 31 ต.ค. 2569), `TST-SN` (serial prefix TS ยาว 8, ยังไม่มีราคา — ใช้ใน 4.8 / R3),
  `TST-SV` (บริการ exempt ทุน 200, ราคา ฿300 **เฉพาะ 13 ต.ค. 2569**); โปร `PRO-T-PCT` (หมวด TS ลด 10% สูงสุด ฿30 ขั้นต่ำ 2 ชิ้น),
  `PRO-T-FREE` (ซื้อ 2 ชิ้นใน TS-A-1 แถม TST-SV ทวีคูณ สูงสุด 3 ชุด)
