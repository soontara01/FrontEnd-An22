## Architecture

- `src/app/core/` — app-wide singletons (`providedIn: 'root'`): auth, `ApiService`, interceptors, shared services, models, `menu.config.ts`.
- `src/app/shared/` — stateless reusable UI (components incl. `StatCard` summary tile, pipes, directives) and `MATERIAL` (common Material modules array).
- `src/app/layout/` — `MainLayout` (toolbar + sidenav + outlet) and `AuthLayout`; both lazy via `loadComponent`.
- `src/app/features/<name>/` — one folder = one lazy module = one menu item.

### Rule: SPA per menu — 1 menu = 1 lazy module = 1 chunk

- **Switching menus is a full page reload.** Cross-menu links (sidenav, links to another feature, login/logout, 404 → home) use plain `href` or `document.location.assign(...)` — never `routerLink` / `router.navigate`. The fresh page boots and downloads only that menu's chunk.
- **Navigation inside one feature is SPA**: use `routerLink` / `router.navigate` (e.g. `/users` ↔ `/users/new` ↔ `/users/:id/edit`).
- Because of the reload, in-memory state (feature stores, signals) lives only for the current menu's page load. Anything that must survive a menu switch goes in `StorageService` (localStorage) — e.g. auth token, theme, mock DB.
- The sidenav highlights the active menu via `MainLayout.activeMenu` (first URL segment), not `routerLinkActive`.
- Sidenav always starts **hidden** on every page load (all screen sizes); ☰ toggles it. Below 960px (`COMPACT_QUERY`) it overlays content, on desktop it pushes content. Not persisted. Content area has no max-width so tables use the full width.
- `core/navigation/menu.config.ts` (`MENU`) is the single source of truth: `app.routes.ts` builds MainLayout children from it, and the sidenav renders from it. Adding a menu = add a `MENU` entry + a `features/<name>/` folder. Do not hand-add feature routes to `app.routes.ts`.
- Each feature exposes `<name>.routes.ts` with a **default export** (`export default [...] satisfies Routes`).
- Inside a feature, pages use `component:` with **static imports**, not `loadComponent`, so the whole feature stays one chunk.
- Page components use `export default class`.
- Feature-scoped services (e.g. `UsersApi`, `UsersStore`) are `@Injectable()` without `providedIn` and are listed in the feature route's `providers` — created once per page load and shared by that feature's pages. Use `providedIn: 'root'` only for things in `core/`.

### Data flow

- Components → feature store (signals) → feature API service → `ApiService` (prefixes `environment.apiUrl`) → `HttpClient`.
- Interceptor order in `app.config.ts`: loading → auth → terminal → branch → error → mockBackend (`branchInterceptor` sends `AuthService.currentBranch()` as `X-Branch-Id` when one is chosen — the mock answers 403 to a branch the user may not work in, a missing header still passes in SaaS step 1 (E2); the toolbar always shows "บริษัท · สาขา"; `terminalInterceptor` sends this device's POS terminal number from `TerminalService` as `X-Terminal-Id` when one is set; shifts, bill numbers and POS IDs are per terminal). The mock must stay **last**; it is only registered when `environment.useMock` is true. It is registered as `lazyMockBackendInterceptor` (`core/interceptors/lazy-mock-backend.interceptor.ts`), which `import()`s `mock-backend.interceptor.ts` on the first request (own lazy chunk, out of the initial bundle; never downloaded when `useMock` is false). Never import `mock-backend.interceptor` statically from app code — only from its specs.
- `errorInterceptor` already shows a snackbar for HTTP errors and logs out on 401 — don't duplicate error toasts in components; just reset local UI state in `error:` callbacks. **Every subscribe that makes an HTTP call has an `error` callback** — reset local state there, else pass `httpErrorShown` (`core/http/http-error-shown.ts`, a no-op) — so a handled error never reaches `GlobalErrorHandler` and the console stays clean (B13; `GlobalErrorHandler` still logs anything unhandled, which is how a missed one shows up). A `switchMap` to HTTP inside a long-lived stream (e.g. `valueChanges`) needs `catchError` inside the `switchMap`, or one error ends the stream.
- **No token, no user** (B3, 2026-10-15; tenant since SaaS step 1): the mock's `requestUser()` resolves only an active user of an active company named by the token (`mockToken(companyId, userId)` = `mock-jwt-token.t<company>.u<user>`; pre-SaaS tokens without a tenant are refused — E1); a missing / unknown token, a suspended company or a deactivated user → **401** on every endpoint except `POST /auth/login` (`auth/verify` stays 400 and checks the login inside the token's company) — never a fallback user. Mock specs send the admin token by default via `asAdminByDefault`.
- **Login = company code + username + password** (D4, SaaS step 1, `auth.model.ts`): `POST /auth/login { companyCode, username, password }` → `{ token, user, company, branches }`; every failure (code / user / password / deactivated) gives the same message (E3), a suspended company is told only after a correct login. `AuthService` keeps `company`, `branches` and `currentBranch` (StorageService `company` / `branches` / `branch`); the device remembers `companyCode` (shown as text + "เปลี่ยน" on the login page) and its `branch` across logouts; one active branch → chosen automatically. A saved session without `company` counts as logged out (E1). **Several branches** (SaaS step 2): `branchGuard` on MainLayout sends a session without a working branch to `/auth/select-branch` (AuthLayout; `login` has `guestGuard`, `select-branch` `authGuard`); the toolbar "บริษัท · สาขา" becomes a menu when the user has more than one branch — `AuthService.selectBranch(id)` + `document.location.reload()` (every menu's state belongs to one branch). MainLayout calls `AuthService.refresh()` (`GET /me`) once per page load, so changed rights apply; a branch taken away → the branch page. POS parked bills are stored per company + branch (`pos.held.<companyId>.<branchId>`; the old `pos.holds` moves into the first branch that opens the POS). Mock: company `DEMO` (name / tax ID read from `storeInfo` until step 2), one branch `HQ` made from `storeInfo` (`ensureBranch()`).
- **SKU master = the `products` collection** (`Product` in `core/models/product.model.ts`), shared by the SKU menu (master data CRUD incl. cost, `features/sku`), the Inventory menu (stock) and the Pricing menu (sale prices, `features/pricing`). Stock changes only via Inventory (`PUT /products/:id/stock`); the SKU form never writes `stock`. Inventory shows only `active` SKUs. `serialControl` is a flag + optional format (`serialPrefix`, `serialLength`).
- **Inventory costing** (`core/models/costing.model.ts`, decided 2026-10-04): **serial SKUs = specific identification** (each `SerialNumber.cost`; issue cost = the removed serials' own costs), **non-serial = moving weighted average** (`movingAverage()` on every receipt; issues go out at the current avg, which stays unchanged). `Product.avgCost` is server-derived (serial: mean of in-stock serial costs). `Product.cost` is only the **standard cost** (default when receiving, estimate when no stock) — never compute inventory value or COGS from it; use `costValue()` / `effectiveCost()` (margins). Every stock change writes a `StockMovement` (stock card, `/inventory/stock-card/:productId`, running balance qty / avg / value; old data gets an `opening` line). An `opening` line is a brought-forward balance, never a receipt (B17): `buildStockCard()` folds the ones at the start of the range into `opening` (returned separately as `openingMovements`, not in `movements` or the totals), so opening + in − out = closing. The stock card is queried by local-date range: `buildStockCard()` returns opening (brought forward) / in-range movements / totals / closing; the page keeps the range in query params (`?from=&to=`, `?all=1`; default = this month) and uses `rxResource`. Receiving requires a cost: non-serial via `StockReceiveDialog` (qty per base or pack unit), serial via the receive dialog's cost-per-unit. A future POS sale line must take COGS from the serial's cost or the current `avgCost` at sale time.
- **Stock per branch** (SaaS step 3, D1, E13–E19): 1 branch = 1 warehouse. `stock` / `avgCost` / `minStock` / `maxStock` live in `branch_stock` (`BranchStock`, `core/models/branch-stock.model.ts`; no row = all 0) and the API fills them into `Product` for the `X-Branch-Id` branch — so every screen, `suggestReorderQty()`, `effectiveCost()` and `priceCart()` work on the current branch without change; `Product.cost` stays company-wide. `StockMovement.branchId`: the stock card is one branch's (never summed — averages differ). The SKU form / Excel edit the current branch's reorder levels. Writes that move stock or sell need `X-Branch-Id` (else 400, E17); deleting a SKU / changing `serialControl` / `itemType` looks at every branch (E18). Mock: `db.products` is filled in per request (`atBranch()`) and written back to `branchStock` before saving (`storeBranchStock()`, like `storeInfo`) — fine while every write happens in the request's branch (transfers, step 5, will need a cross-branch helper); `migrateBranchStock()` moved older data into the first branch once and gave BN sample stock.
- **Serial SKUs: stock = count of `in_stock` serials** (`SerialNumber` in `core/models/serial.model.ts`). Stock moves only via receive/remove serial endpoints (Inventory dialogs in `features/inventory/dialogs/`); `PUT /products/:id/stock` is rejected for them, and `serialControl` cannot change while stock > 0. Removing never deletes: status becomes sold/damaged/other with `removedAt` + note (history); re-receiving a removed serial puts it back in stock — the same record is reused (status / note overwritten; its note and the receive line's note say "รับคืนเข้าคลัง" unless one is typed), so a serial's history is read from the stock movements with `serialMovements()` (`serial.model.ts`; Inventory → ประวัติ Serial, click a serial) — no history field on `SerialNumber` (B18). `serialFormatError()` is the single format rule for UI and mock. The mock auto-generates sample serials when a serial SKU has more stock than serials. **A serial stands in one branch** (`SerialNumber.branchId`, E16; numbers unique company-wide): `GET /products/:id/serials` lists the current branch's, and selling / free goods / an exchange's new unit / removing take only a unit in stock here (another branch's → 400 naming it); returns go back into the document's branch. Until transfers (step 5) a unit moves by removing it at one branch and receiving it at the other (the record follows).
- Dialogs that need a route-scoped service (e.g. `InventoryStore`) must be opened with `injector: this.injector` — `MatDialog` otherwise uses the root injector. Shared helpers `stockLevel()` / `PRODUCT_DEFAULTS` live in the model file — don't import between features.
- **SKU retail fields** (`product.model.ts`): `categoryId` must be an **active leaf** category (3 levels: แผนก > หมวด > หมวดย่อย, `category.model.ts`); `categoryPath` is server-derived/read-only. `vatType` (`vat7` | `exempt`): prices are VAT-inclusive, cost excludes VAT, and **margin is computed on the net price** — always use `vatBreakdown()` / `marginPercent()`. `shortName` ≤ 20 chars (receipt). `imageUrl` is a resized data URL (`shared/utils/image-resize.ts`, max 400px). `packUnits` (unit, factor > 1, barcode) — **serial SKUs have exactly one unit**; stock is always counted in the base unit (`stockInPacks()` for display). **Every barcode (base + packs) is unique across all SKUs.** `saleStatus` (`SkuStatus`): active / no_sale (purchase only) / no_purchase (sell remaining, receiving blocked) / discontinued (hidden from Inventory & Pricing) — use `canSell()` / `canPurchase()` / `isDiscontinued()`, never compare strings ad hoc. Note `SaleStatus` is the _sales order_ status (`sale.model.ts`); the SKU one is `SkuStatus`.
- **ข้อมูลหลัก menu** (`features/master-data`): tab shell (`MasterDataShell`) + child route per master (หมวดหมู่, ผู้จำหน่าย, ช่องทางชำระเงิน, เครื่อง POS, สาขา). `Supplier` (`supplier.model.ts`): Thai tax ID must pass `isValidThaiTaxId()`, head office or 5-digit branch, `creditDays` (0 = cash); unique by code and by taxId+branch; cannot be deleted while linked to SKUs (deactivate instead).
- **SKU ↔ supplier**: `Product.suppliers: SkuSupplier[]` (supplierSku, purchase cost excl. VAT, leadTimeDays, moq in base units); when not empty exactly one `isMain`. Reorder: `minStock` = reorder point, `maxStock` = target (0 → 2 × reorder point, must be ≥ reorder point). `suggestReorderQty()` is the only reorder rule (purchasable + stock ≤ reorder point → fill to max, ≥ main MOQ, rounded up to the smallest pack). The reorder page is `/inventory/reorder` (grouped by main supplier, printable). Categories are deletable only without children/SKUs; a category with SKUs cannot get children.
- **Service SKUs** (`Product.itemType`: `stock` | `service`, decided 2026-10-04): e.g. installation, repair labour, eSIM activated at the operator on sale. A service is a normal SKU (SKU + Pricing menus, VAT, `saleStatus`) but **never has stock**: no movements/serials/packs/reorder levels — `withServiceRules()` clears those fields (used by the SKU form, Excel import and the mock); stock/serial endpoints reject it; hidden from the Inventory menu (store, reorder, receipt import). Its `cost` is the cost of each sale (COGS) — `effectiveCost()` already returns it since stock is always 0. `itemType` cannot change while stock > 0. Use `isService()`, never compare the string. Pre-bought codes (eSIM QR / gift cards bought in lots) are _not_ services: use a serial-controlled stock SKU.
- **Promotions** (menu โปรโมชั่น, `features/promotions`, model `core/models/promotion.model.ts`, decided 2026-10-04): master data for the future POS. Types `item_discount` (per-unit % or ฿ on qualifying items, `minQty` per line, % may have `maxDiscount`), `bill_discount` (whole bill once ≥ `minAmount`; scope is always `all`), `free_goods` (per set of `minQty` pieces **or** `minAmount` baht of qualifying items → `freeGoods.items`; `repeat` multiplies, `maxSets` caps). Scope = `all` or `productIds` + `categoryIds` (a category covers everything below it — use `inScope()`). **Branches** (D2, SaaS step 2): `branchIds` ([] = every branch) — `inBranch()` filters in `promotionsForProduct()` and `priceCart()` (`PricingContext.branchId` = the sale's branch; POS sends the current one, the server `X-Branch-Id`; unknown branch → limited promotions never apply); only company admins create / edit / delete a branch-limited one (`promotionBranchScopeError()` → 403); `branchIds` lock with the other fields once started. Periods use the price date helpers (local `YYYY-MM-DD`, inclusive, `endDate: null` = open); promotions **may overlap**. Status via `promotionStatus()` (`enabled: false` → disabled). `promotionError()` is the single rule for form + mock; once started (`hasStarted()`) only `enabled`, a shorter `endDate` (≥ today) and `note` may change, and it cannot be deleted (disable instead). SKUs / categories used by a non-expired promotion cannot be deleted. Free items must be sellable (`canSell`); services are allowed. Preview math (discounted price, margin net of VAT vs `effectiveCost()`, free-set cost) is in `features/promotions/data/promotion-preview.ts`. **POS rules (to implement there):** a promotion applies when active on the sale date; per item/bill, candidates are taken by `priority` (high first, `promotionsForProduct()`), a non-stackable one stops lower ones, stackable ones combine; item discounts first, then bill discount on the discounted total; free items are 0-price lines that still issue stock and take COGS (serial free items need their serial scanned). The sale line should record the promotion id.
- **Payment methods** (tab ช่องทางชำระเงิน `/master-data/payment-methods`, model `core/models/payment-method.model.ts`, decided 2026-10-04) = the POS tender buttons, ordered by `sortOrder` (changed only via `PUT /payment-methods/order { ids }`; list page ▲▼ + button preview; form is a dialog). Types: cash / card / qr / transfer / e_wallet / installment / other. Status labels/badges: `SALE_STATUS_LABEL` / `SALE_STATUS_BADGE`.
- **Credit notes** (ใบลดหนี้, `core/models/credit-note.model.ts`, decided 2026-10-04): returns of a paid POS bill from the day _after_ the sale (same day → void). The bill never changes; a `CreditNote` (`CN-YYYYMMDD-NNNN`) refers to it. Refund per line = its share of `amount` (discounts already in it, bill discount not re-checked; the last units take the exact remainder). Free goods are re-checked with `freeSets()` on what the customer keeps — kept free units no longer earned are deducted at `SaleLine.listPrice` (never twice). Money back in cash or through the bill's own methods up to what they took minus earlier refunds (`refundOptions()`). Returned goods go back at their sale COGS or are written off (serial → damaged); services never restock. `draftCreditNote()` / `creditNoteError()` are the single rule (form + mock). Admin only (page `/sales/:id/credit-note`). Sales-list totals subtract credit notes of the period. The bill's `status` stays `paid`; `Sale.returnStatus` (none / partial / full), `creditedTotal` and `creditNoteNos` are read-only, server-derived on every read from all its credit notes (`returnSummary()`) — the list shows a second badge (`RETURN_STATUS_LABEL` / `_BADGE`), the refunded amount under the total and a "มีใบลดหนี้" filter.
- **Exchanges** (ใบเปลี่ยนสินค้า, `core/models/exchange.model.ts`, decided 2026-10-05): swap units of a paid POS bill for the **same SKU and unit** — same price, so no money, no credit note, no new invoice; the bill never changes. Any staff member within `StoreInfo.exchangeDays` of the sale day (Settings; 0 = no limit; admins any time); `exchangeBlocker()` / `exchangeError()` are the single rule (form + mock). The replacement must be in stock **before** the exchange (`ctx.products`; returned units never count — same rule as the POS) and is issued **first**, like a sale (serial: own cost; others: current avg); only then does the old unit come back into stock (serial: own cost; others: the line's sale COGS share) or get written off (serial → damaged) — `costIn` / `costOut` are on the line, the bill's COGS stays. Serial warranty keeps counting from the sale day (`warrantyEnd()`). **The serial the customer holds is `currentSerial(sale, index, exchanges)`** — credit notes (`draftCreditNote(..., exchanges)`) and void return that one, never `line.serial` directly. `Sale.exchangeNos` is server-derived. Page `/sales/:id/exchange`, 80 mm `ExchangeReceipt` (`shared/components/receipt`), bill page `?printEx=<id>`.
- **Full tax invoice** (ใบกำกับภาษีเต็มรูป, `core/models/tax-invoice.model.ts`, decided 2026-10-04): issued on request instead of the abbreviated one — one per paid POS bill of a VAT-registered store (`taxInvoiceError()`, form + mock). Buyer details are typed on the invoice (no customer master); the buyer's head office / branch is needed only for VAT-registered buyers — `branchType: 'none'` (default for a national ID, `defaultBuyerBranch()`) prints nothing, show it via `buyerBranchLabel()`; a foreign buyer without a Thai tax ID uses `idType: 'passport'` (passport no. kept in `taxId`, no branch; `buyerIdError()` / `buyerIdLabel()` / `buyerIdShort()`, missing `idType` = `tax_id`); amounts always come from the bill; `Sale.taxInvoiceNo` is server-set; voiding the bill cancels it (`cancelledAt`); credit notes print the number valid when they were issued and never change (the bill page flags a cancelled one with its replacement via `invoiceRefState()`). Printed as original / copy on A4 (`TaxInvoiceDocument`, `printElement(el, 'A4')`) or 80 mm (`TaxInvoiceSlip`, `printElement(el)`), both in `shared/components/tax-invoice`; `StoreInfo.taxInvoicePaper` is the default (the POS uses it, the bill page can switch); VAT split via `invoiceTotals()`, total in words via `bahtText()` (`shared/utils/baht-text.ts`). Two ways: **with the sale** — the POS "ขอใบกำกับภาษีเต็มรูป" button collects the buyer (`BuyerDialog`, `checkoutBuyerError()`), `SalePayload.buyer` makes `POST /sales` issue it in the same request dated at the sale (`TaxInvoice.atSale`, no abbreviated invoice, the internal `POS-…` number is not printed; the POS prints the A4 invoice instead of the 80 mm slip); or **later** on page `/sales/:id/tax-invoice` (in place of the abbreviated one; no time limit). Wrong buyer details are never edited: admins **cancel and reissue** (`reissueError()`, page `?reissue=1`) — the old one gets `cancelledAt` / `cancelReason` / `replacedByNo`, the new one a new number (same sale day, same amounts, same `atSale`) and `replacesInvoiceNo`; `currentInvoice()` picks the valid one. Either way it is dated and numbered on the **sale day** (`INV-<sale day>-NNNN`; accountant's decision 2026-10-04) and `issuedAt` records when it was really issued. Once a bill has one, its 80 mm `Receipt` prints as a plain receipt referring to it.

## Conventions

- Standalone components, `ChangeDetectionStrategy.OnPush`, `inject()` (no constructor injection), `input()`/`output()`/`viewChild()` signal APIs, `@if`/`@for` control flow.
- State: `signal` / `computed` in services; expose read-only via `.asReadonly()`. No NgRx.
- Forms: Reactive forms via `NonNullableFormBuilder`. A typed baht amount is checked by `moneyProblem()` / `moneyInputError(value, label)` (`core/models/money.model.ts`: empty → "กรุณากรอก…", negative → "…ต้องไม่ติดลบ", > 2 decimals → "…ทศนิยมไม่เกิน 2 ตำแหน่ง"; B1 / B14) — reactive controls use `moneyValidator` + `moneyErrorText()` (`shared/utils/money-validator.ts`); an empty number field must never turn into a silent 0. `<mat-error>` only shows for a form control: a signal-bound input shows its error as `<mat-hint class="field-error">`.
- Route params bind to component inputs (`withComponentInputBinding()`), e.g. `readonly id = input<string>()`.
- Imports use aliases `@core/*`, `@shared/*`, `@layout/*`, `@features/*`, `@env/*`; relative imports only within the same feature/folder.
- Styling: use Material system tokens (`var(--mat-sys-*)`), not hard-coded colors, so dark mode (`html.dark-theme`, toggled by `ThemeService`) works.
- Global helper classes in `styles.scss`: `.stat-grid` (layout for `<app-stat-card>`), `.filter-row` (search/filter controls above a table), `.badge` + `.badge-success|warn|error` (status pills). Reuse them instead of per-component copies.
- Money: `currency: 'THB' : 'symbol-narrow' : '1.0-0'`; dates: `thaiDate` pipe.
- mat-table rows are untyped (`let x` is `any`), so strict templates cannot index a `Record` with them — use a typed helper method (e.g. `statusText(sale: Sale)`).
- Icons: Material Symbols Outlined (set as default font set in `app.config.ts`).
- UI text is Thai; code, identifiers and comments are English.
- Selector prefix `app-` (components) / `app` camelCase (directives).

## Gotchas

- TypeScript 6: don't add `baseUrl` to tsconfig (deprecated); `paths` are relative to `tsconfig.json`.
- `CanMatchFn` in Angular 22 takes 3 args (`route, segments, currentSnapshot`) — tests must pass a third.
- No `@angular/animations` package; Material 22 doesn't need it — don't add `provideAnimationsAsync()`.
- Initial bundle budget is 600 kB warning / 1 MB error (`angular.json`). Keep heavy Material modules out of eagerly loaded code (`core` services, `app.ts`).
- `AuthService` inlines `isCompanyAdmin()` / `normalizeCompanyCode()` on purpose: importing `user.model` / `company.model` put them (3–5 kB) into the initial bundle — keep runtime imports in eager code to tiny model files.
- Eagerly loaded code (`app.routes.ts`, guards, root services it reaches) must import runtime values from the model file itself (e.g. `@core/models/menu-access.model`), never the `@core/models` barrel — the barrel pulled ~60 kB into the initial bundle (605 kB, over budget). Type-only imports from the barrel are fine.
- `DatePipe` / `formatDate` in a feature moves `@angular/common`'s locale formatting (~9 kB) into the shared _initial_ chunk — use the `thaiDate` pipe or a small helper instead; compare "Initial total" before/after a change.
- `AuthService.logout()` and login success call `document.location.assign` (inject `DOCUMENT`); in tests provide a stub `DOCUMENT` with `location.assign = vi.fn()`.
- Tests use Vitest globals (`vi`, `describe`, …); HTTP tests use `provideHttpClientTesting()` and `HttpTestingController`.

## Switching to a real backend

Set `useMock: false` in `src/environments/environment*.ts`; dev proxy `proxy.conf.json` forwards `/api` → `http://localhost:8080`. SPA deploy configs are in `deploy/`.

The real backend lives in separate repos (db = PostgreSQL scripts, api = Java Spring Boot, web = Node.js static server); this repo is their spec. **Hand-off docs: `docs/backend/`** — `README.md` (repos, how they read this one), `api-contract.md` (every endpoint, headers, errors, 401/403 rules — the former endpoint list), `domain-rules.md` (rule functions the server must port, incl. mock-only rules), `data-model.md` (tables, keys, derived fields, document numbers); decision index `docs/decisions.md`.

**Keep them current:** adding / changing an endpoint, a stored field, a permission or a rule in `core/models` or the mock → update the matching `docs/backend/*.md` (and `docs/decisions.md` for a new decision) in the same commit; a changed calculation rule also gets `npm run fixtures` (+ a new case in `golden-fixtures.ts` for the change).
