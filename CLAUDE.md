## Architecture

- `src/app/core/` — app-wide singletons (`providedIn: 'root'`): auth, `ApiService`, interceptors, shared services, models, `menu.config.ts`.
- `src/app/shared/` — stateless reusable UI (components incl. `StatCard` summary tile, pipes, directives) and `MATERIAL` (common Material modules array).
- `src/app/layout/` — `MainLayout` (toolbar + sidenav + outlet) and `AuthLayout`; both lazy via `loadComponent`.
- `src/app/features/<name>/` — one folder = one lazy module = one menu item.

### Rule: SPA per menu — 1 menu = 1 lazy module = 1 chunk

- **Switching menus is a full page reload.** Cross-menu links (sidenav, links to another feature, login/logout, 404 → home) use plain `href` or `document.location.assign(...)` — never `routerLink` / `router.navigate`. The fresh page boots and downloads only that menu's chunk.
- **Navigation inside one feature is SPA**: use `routerLink` / `router.navigate` (e.g. `/users` ↔ `/users/new` ↔ `/users/:id/edit`).
- Because of the reload, in-memory state (feature stores, signals) lives only for the current menu's page load. Anything that must survive a menu switch goes in `StorageService` (localStorage) — e.g. auth token, theme, mock DB.
- The sidenav highlights the active menu via `MainLayout.activeMenu` (first URL segment), not `routerLinkActive`.
- Sidenav always starts **hidden** on every page load (all screen sizes); ☰ toggles it. Below 960px (`COMPACT_QUERY`) it overlays content, on desktop it pushes content. Not persisted. Content area has no max-width so tables use the full width.
- `core/navigation/menu.config.ts` (`MENU`) is the single source of truth: `app.routes.ts` builds MainLayout children from it, and the sidenav renders from it. Adding a menu = add a `MENU` entry + a `features/<name>/` folder. Do not hand-add feature routes to `app.routes.ts`.
- Each feature exposes `<name>.routes.ts` with a **default export** (`export default [...] satisfies Routes`).
- Inside a feature, pages use `component:` with **static imports**, not `loadComponent`, so the whole feature stays one chunk.
- Page components use `export default class`.
- Feature-scoped services (e.g. `UsersApi`, `UsersStore`) are `@Injectable()` without `providedIn` and are listed in the feature route's `providers` — created once per page load and shared by that feature's pages. Use `providedIn: 'root'` only for things in `core/`.

### Data flow

- Components → feature store (signals) → feature API service → `ApiService` (prefixes `environment.apiUrl`) → `HttpClient`.
- Interceptor order in `app.config.ts`: loading → auth → terminal → error → mockBackend (`terminalInterceptor` sends this device's POS terminal number from `TerminalService` as `X-Terminal-Id` when one is set; shifts, bill numbers and POS IDs are per terminal). The mock must stay **last**; it is only registered when `environment.useMock` is true. It is registered as `lazyMockBackendInterceptor` (`core/interceptors/lazy-mock-backend.interceptor.ts`), which `import()`s `mock-backend.interceptor.ts` on the first request (own lazy chunk, out of the initial bundle; never downloaded when `useMock` is false). Never import `mock-backend.interceptor` statically from app code — only from its specs.
- `errorInterceptor` already shows a snackbar for HTTP errors and logs out on 401 — don't duplicate error toasts in components; just reset local UI state in `error:` callbacks. **Every subscribe that makes an HTTP call has an `error` callback** — reset local state there, else pass `httpErrorShown` (`core/http/http-error-shown.ts`, a no-op) — so a handled error never reaches `GlobalErrorHandler` and the console stays clean (B13; `GlobalErrorHandler` still logs anything unhandled, which is how a missed one shows up). A `switchMap` to HTTP inside a long-lived stream (e.g. `valueChanges`) needs `catchError` inside the `switchMap`, or one error ends the stream.
- **No token, no user** (B3, 2026-10-15): the mock's `requestUser()` resolves only an active user named by the token (`mock-jwt-token` = admin, `mock-jwt-token.u<id>`); a missing / unknown token or a deactivated user → **401** on every endpoint except `POST /auth/login` (`auth/verify` stays 400) — never a fallback user (SaaS reads the company from the token). Mock specs send the admin token by default via `asAdminByDefault`.
- **SKU master = the `products` collection** (`Product` in `core/models/product.model.ts`), shared by the SKU menu (master data CRUD incl. cost, `features/sku`), the Inventory menu (stock) and the Pricing menu (sale prices, `features/pricing`). Stock changes only via Inventory (`PUT /products/:id/stock`); the SKU form never writes `stock`. Inventory shows only `active` SKUs. `serialControl` is a flag + optional format (`serialPrefix`, `serialLength`).
- **Inventory costing** (`core/models/costing.model.ts`, decided 2026-10-04): **serial SKUs = specific identification** (each `SerialNumber.cost`; issue cost = the removed serials' own costs), **non-serial = moving weighted average** (`movingAverage()` on every receipt; issues go out at the current avg, which stays unchanged). `Product.avgCost` is server-derived (serial: mean of in-stock serial costs). `Product.cost` is only the **standard cost** (default when receiving, estimate when no stock) — never compute inventory value or COGS from it; use `costValue()` / `effectiveCost()` (margins). Every stock change writes a `StockMovement` (stock card, `/inventory/stock-card/:productId`, running balance qty / avg / value; old data gets an `opening` line). The stock card is queried by local-date range: `buildStockCard()` returns opening (brought forward) / in-range movements / totals / closing; the page keeps the range in query params (`?from=&to=`, `?all=1`; default = this month) and uses `rxResource`. Receiving requires a cost: non-serial via `StockReceiveDialog` (qty per base or pack unit), serial via the receive dialog's cost-per-unit. A future POS sale line must take COGS from the serial's cost or the current `avgCost` at sale time.
- **Serial SKUs: stock = count of `in_stock` serials** (`SerialNumber` in `core/models/serial.model.ts`). Stock moves only via receive/remove serial endpoints (Inventory dialogs in `features/inventory/dialogs/`); `PUT /products/:id/stock` is rejected for them, and `serialControl` cannot change while stock > 0. Removing never deletes: status becomes sold/damaged/other with `removedAt` + note (history); re-receiving a removed serial puts it back in stock. `serialFormatError()` is the single format rule for UI and mock. The mock auto-generates sample serials when a serial SKU has more stock than serials.
- Dialogs that need a route-scoped service (e.g. `InventoryStore`) must be opened with `injector: this.injector` — `MatDialog` otherwise uses the root injector. Shared helpers `stockLevel()` / `PRODUCT_DEFAULTS` live in the model file — don't import between features.
- **SKU retail fields** (`product.model.ts`): `categoryId` must be an **active leaf** category (3 levels: แผนก > หมวด > หมวดย่อย, `category.model.ts`); `categoryPath` is server-derived/read-only. `vatType` (`vat7` | `exempt`): prices are VAT-inclusive, cost excludes VAT, and **margin is computed on the net price** — always use `vatBreakdown()` / `marginPercent()`. `shortName` ≤ 20 chars (receipt). `imageUrl` is a resized data URL (`shared/utils/image-resize.ts`, max 400px). `packUnits` (unit, factor > 1, barcode) — **serial SKUs have exactly one unit**; stock is always counted in the base unit (`stockInPacks()` for display). **Every barcode (base + packs) is unique across all SKUs.** `saleStatus` (`SkuStatus`): active / no_sale (purchase only) / no_purchase (sell remaining, receiving blocked) / discontinued (hidden from Inventory & Pricing) — use `canSell()` / `canPurchase()` / `isDiscontinued()`, never compare strings ad hoc. Note `SaleStatus` is the _sales order_ status (`sale.model.ts`); the SKU one is `SkuStatus`.
- **ข้อมูลหลัก menu** (`features/master-data`): tab shell (`MasterDataShell`) + child route per master (หมวดหมู่, ผู้จำหน่าย, ช่องทางชำระเงิน, เครื่อง POS). `Supplier` (`supplier.model.ts`): Thai tax ID must pass `isValidThaiTaxId()`, head office or 5-digit branch, `creditDays` (0 = cash); unique by code and by taxId+branch; cannot be deleted while linked to SKUs (deactivate instead).
- **SKU ↔ supplier**: `Product.suppliers: SkuSupplier[]` (supplierSku, purchase cost excl. VAT, leadTimeDays, moq in base units); when not empty exactly one `isMain`. Reorder: `minStock` = reorder point, `maxStock` = target (0 → 2 × reorder point, must be ≥ reorder point). `suggestReorderQty()` is the only reorder rule (purchasable + stock ≤ reorder point → fill to max, ≥ main MOQ, rounded up to the smallest pack). The reorder page is `/inventory/reorder` (grouped by main supplier, printable). Categories are deletable only without children/SKUs; a category with SKUs cannot get children.
- **Service SKUs** (`Product.itemType`: `stock` | `service`, decided 2026-10-04): e.g. installation, repair labour, eSIM activated at the operator on sale. A service is a normal SKU (SKU + Pricing menus, VAT, `saleStatus`) but **never has stock**: no movements/serials/packs/reorder levels — `withServiceRules()` clears those fields (used by the SKU form, Excel import and the mock); stock/serial endpoints reject it; hidden from the Inventory menu (store, reorder, receipt import). Its `cost` is the cost of each sale (COGS) — `effectiveCost()` already returns it since stock is always 0. `itemType` cannot change while stock > 0. Use `isService()`, never compare the string. Pre-bought codes (eSIM QR / gift cards bought in lots) are _not_ services: use a serial-controlled stock SKU.
- **Promotions** (menu โปรโมชั่น, `features/promotions`, model `core/models/promotion.model.ts`, decided 2026-10-04): master data for the future POS. Types `item_discount` (per-unit % or ฿ on qualifying items, `minQty` per line, % may have `maxDiscount`), `bill_discount` (whole bill once ≥ `minAmount`; scope is always `all`), `free_goods` (per set of `minQty` pieces **or** `minAmount` baht of qualifying items → `freeGoods.items`; `repeat` multiplies, `maxSets` caps). Scope = `all` or `productIds` + `categoryIds` (a category covers everything below it — use `inScope()`). Periods use the price date helpers (local `YYYY-MM-DD`, inclusive, `endDate: null` = open); promotions **may overlap**. Status via `promotionStatus()` (`enabled: false` → disabled). `promotionError()` is the single rule for form + mock; once started (`hasStarted()`) only `enabled`, a shorter `endDate` (≥ today) and `note` may change, and it cannot be deleted (disable instead). SKUs / categories used by a non-expired promotion cannot be deleted. Free items must be sellable (`canSell`); services are allowed. Preview math (discounted price, margin net of VAT vs `effectiveCost()`, free-set cost) is in `features/promotions/data/promotion-preview.ts`. **POS rules (to implement there):** a promotion applies when active on the sale date; per item/bill, candidates are taken by `priority` (high first, `promotionsForProduct()`), a non-stackable one stops lower ones, stackable ones combine; item discounts first, then bill discount on the discounted total; free items are 0-price lines that still issue stock and take COGS (serial free items need their serial scanned). The sale line should record the promotion id.
- **Payment methods** (tab ช่องทางชำระเงิน `/master-data/payment-methods`, model `core/models/payment-method.model.ts`, decided 2026-10-04) = the POS tender buttons, ordered by `sortOrder` (changed only via `PUT /payment-methods/order { ids }`; list page ▲▼ + button preview; form is a dialog). Types: cash / card / qr / transfer / e_wallet / installment / other. Fields: `requireReference` + `referenceLabel`, `minAmount` / `maxAmount` per payment line, `feePercent` (MDR, for net-received reports via `netReceived()`; 0 for cash), cash-only `cashRounding` (`roundCash()`: none / nearest 0.25 / nearest baht), qr-only `promptPayId` (`isValidPromptPayId()`: mobile 10 digits or checksum-valid tax ID), qr/transfer `bankAccount`, installment-only `installmentMonths`. `withPaymentTypeRules()` clears fields the type doesn't use (form + mock); `paymentMethodError()` is the single rule. There must always be one active cash method (`isLastActiveCash()`: it cannot be deactivated, retyped or deleted). Credit sales / vouchers / surcharges are out of scope (need a customer master / voucher system). **POS rules (to implement there):** a bill may be split over several active methods; only cash (`allowsChange()`) may exceed its share — the excess is change, and only the cash part is rounded; each line must be within the method's min/max; the cash drawer opens only for cash (`opensDrawer()`); a payment line records method id, amount, reference and installment months. Once sales reference a method it must not be deleted (deactivate instead).
- **Excel** (ExcelJS): load it only via `loadExcel()` from `shared/utils/excel.ts` (also `xlsxBlob`, `styleHeaderRow`) — never a static import, it is ~1 MB and must stay in its own lazy chunk; `import type` is fine. Two importers share the same pattern (template download → header-matched read → client-side validate with per-row errors → save valid rows/groups one by one with `concatMap`, a failure doesn't stop the rest): SKU master (`features/sku/data/sku-excel.ts`, below) and **goods receipt** (`features/inventory/data/receive-excel.ts`, page `/inventory/receive-import`: normal SKUs = qty (+ pack unit), serial SKUs = one row per serial; cost per entered unit, blank = main supplier cost; serial rows merged into one `receiveSerials` call per SKU/cost/note).
- SKU master Excel (`features/sku/data/sku-excel.ts`): Columns are defined once in `SKU_COLUMNS` (Thai headers; `info` = reference-only, ignored on import). Import matches by SKU code (exists → update, blank cells keep the old value; new → create with defaults), validates everything client-side in `validateImportRows()` (mirrors server rules) before saving, and saves valid rows one by one. Codes/barcodes are written as text (`numFmt '@'`). Pages: `/sku/import`, export from the SKU list menu.
- **POS manual discounts** (ส่วนลดพิเศษ, decided 2026-10-10): per line (`CartItem.manualDiscount`) and per bill (`SalePayload.billManualDiscount`), each `ManualDiscount` = % or baht, taken **after every promotion** (step 6 of `priceCart()`; promotions and their eligibility never change). The bill one is taken on what is left after line manual discounts and allocated pro rata like the promo bill discount; `SaleLine.manualDiscount` = own + bill share, and `amount = gross − itemDiscount − billDiscount − manualDiscount`. Below cost after it → warning only. `manualDiscountError()` (POS + mock): a reason is always required (one per bill, `Sale.manualDiscountReason`, giver in `manualDiscountBy`), staff may give at most `StoreInfo.manualDiscountMaxPercent` (default 5, 0 = none) of each line's price after promotions, admins any. Dialog `features/pos/dialogs/discount-dialog` (preview via `manualDiscountBaht()` / `manualDiscountValueError()` — don't redo the math). Receipt, tax invoices and the bill page include it in the discounts.
- **POS shifts** (เปิด/ปิดกะ, `core/models/shift.model.ts`, decided 2026-10-11, `docs/shift-plan.md`): 1 shift = 1 terminal (cash drawer) + 1 cashier; the terminal is this device's registered terminal (**POS terminals** below), sent as `X-Terminal-Id` by `terminalInterceptor`. When `StoreInfo.requireShift` is on (default; Settings, cannot be turned off while a shift is open — `requireShiftChangeError()`), every sale / void / credit-note refund / cash movement needs the terminal's open shift — `shiftBlocker(action, …)` is the single rule (POS + mock): only its cashier sells, admins may void / refund / move cash in someone else's shift; exchanges need no shift. Money counts in the shift **where it happens** (`Sale.shiftId`, `voidShiftId`, `CreditNote.shiftId`, `Exchange.shiftId` — optional, missing = no shift). `expectedByMethod()` is the expected amount per method (every cash method = one drawer line with the opening float and `CashMovement`s). Closing (`/pos/shift-close`) is a **blind count**: the cashier sees only `ShiftSummary.checklist` (no amounts; non-admins never get `lines` while the shift is open), `count-check` reveals variances after a complete count (`countInputsError()` / `countCheck()`; a non-cash `count` line is the evidence's net amount and may be negative when refunds exceed takings — S9 / B23; cash ≥ 0), one recount (`firstCount` kept), a `VarianceReason` for every variance, approval when any single method is off by more than `shiftVarianceLimit` (an admin closing approves, or an admin login typed at the terminal — `approval { username, password }`, checked by the server; else `pending`, approved later on `/sales/shifts/:id`). Per-method check at close = `closeCheckOf()` (`PaymentMethod.closeCheck` count / confirm / none, type default, cash always count). `closeShiftError()` / `openShiftError()` / `cashMovementError()` are the single rules (`cashMovementError(p, expectedCash, isAdmin)` names the expected cash only to admins — B19, blind count; `CashMovementDialog` saves itself and stays open with the typed values when the server refuses). Shifts belong to their opening day (`shiftDay()`), sales/tax keep the bill date; `shiftOpenTooLong()` (`shiftMaxHours`) only warns. Z report = shared `ShiftSlip` (80 mm); X report dialog in the POS; lock screen = `PosStore.lock()` / `unlock()` via `auth/verify` (localStorage `pos.locked`). Sales menu: `/sales/shifts` (range, pending filter, variance per cashier via `varianceReport()`) and `/sales/shifts/:id`. An admin closes **another terminal's** open shift (cashier left without closing) from `/sales/shifts/:id` → "ปิดกะแทน" → `/pos/shift-close?shift=<id>` (same blind count; `count-check` / `close` don't check `X-Terminal-Id`; this terminal's own shift and lock stay). The bill list filters by shift with `/sales?shift=<id>` (bills sold or voided in it + its credit-note refunds; ignores the date range). **Drawer opened without a sale** (S7, decided 2026-10-12): POS shift menu → `DrawerOpenDialog`, same who / where rule as a cash movement (`shiftBlocker('drawer_open')`), reason required (`drawerOpenError()`); stored as `DrawerOpen` (not a `CashMovement` — no money, expected amounts untouched); counted in `ShiftSummary.drawerOpenCount` (X / Z) and `VarianceReportRow.drawerOpens`. **Adjusting a closed shift** (S8): admins add a `ShiftAdjustment` (+ / − on a method that was counted, `AdjustmentReason`, `shiftAdjustmentError()`) from `/sales/shifts/:id` — recorded separately, never edited / deleted; counts, the original Z, `floatLeft` and the approval status never change; `adjustedVariance()` gives the variance after them (shift page, shift list via server-derived `Shift.adjustmentTotal`, Z copy section via `ShiftSlip [adjustments]`, `varianceReport(shifts, { adjustments, drawerOpens })`).
- **POS terminals** (`core/models/pos-terminal.model.ts`, decided 2026-10-12, `docs/terminal-plan.md`): registry `PosTerminal { id = terminal number, name, posId (Revenue Dept POS ID), active }`, tab เครื่อง POS `/master-data/terminals` (admins edit; `posTerminalError()` form + mock; the number never changes; cannot be deleted once a shift / document refers to it, nor deactivated with an open shift; a VAT store's active terminal without a POS ID only warns — `missingPosId()`). A device is set **once by an admin** in Settings → "เครื่องนี้" (`TerminalService`, localStorage `pos.terminal`, null = not set; locked while that terminal has an open shift) — cashiers never type it. Only an active registered terminal may sell or open a shift (`terminalError()`, POS + mock: `POST /sales` / `POST /shifts/open` → 400); the POS shows a banner and blocks paying. Documents keep a snapshot `terminalId` + `posId` (`Sale`, `CreditNote`, `Exchange`; `Shift.posId`) and receipts / 80 mm tax invoices / Z reports print **that** POS ID — `StoreInfo` has no `posId` any more. POS bill numbers run continuously **per terminal and day**: `POS<terminal>-YYYYMMDD-NNNN` (`terminalOrderPrefix()`, T4); `INV-` / `CN-` / `EX-` stay store-wide. Older data: the mock migrates once (`migrateTerminals()`: a terminal per number used by shifts, terminal 1 gets the old store POS ID, kept as `legacyPosId` and filled into older documents on read; old bills keep `POS-YYYYMMDD-NNNN` and count as terminal 1). Bill page / shift pages show `terminalLabel()`; the bill list filters by terminal.
- **Permissions** (admin / user, decided 2026-10-15, table in `docs/saas-plan.md` section 17; user = cashier / stock clerk): the server is the guard — the mock's `adminOnlyError()` answers **403** (Thai message) to non-admins for: all of `/users`; writes (non-GET) of categories, suppliers, payment methods (incl. order), prices, promotions, POS terminals; taking stock out (`PUT /products/:id/stock` with `delta < 0`, `serials/remove`); credit notes; tax-invoice reissue; `GET /tax-invoices` (sales tax report); `PUT /settings/store`; shift approve / adjustments. Shift-level rules in `handleShifts`: a non-admin reads only **their own shifts** (`GET /shifts`, `variance-report` filtered; another's `/shifts/:id…` or count-check / close → 403; `shifts/current` and `GET /shifts/last-float` stay open). **Void**: a non-admin sends `approval { username, password }` of an admin typed at the terminal (missing → 403, wrong / not admin → 400, like shift close); `Sale.voidedBy` / `voidApprovedBy` are server-set. Open to users: SKU master incl. delete / Excel, receiving, selling, manual discounts (≤ max %), exchanges, later tax invoices, cash movements; cost / profit stay visible until SaaS. `userChangeError()` (`user.model.ts`, form + mock): nobody demotes / deactivates / deletes themselves, the last active admin stays. UI: `AuthService.isAdmin` (don't compare `role` ad hoc); admin-only menus via `MenuItem.adminOnly` (hidden in the sidenav + `adminGuard`), admin-only pages inside a feature via `canMatch: [adminGuardTo('/<menu>')]` (redirect stays in that menu); view-only screens hide the write buttons and show `<app-admin-only-note>` (`shared/components/admin-only-note`). `auth/verify` stays 400, never 401 / 403.
- **Sales menu** (`features/sales`): bill list `/sales?from=&to=` (`?all=1`, default today; range presets from `shared/utils/date-range.ts`, also used by the stock card) with `summarizeSales()` (paid total, gross profit of POS bills = net of VAT − COGS, cancelled, money in per payment method); bill page `/sales/:id` (lines with cost/profit, receipt copy, same-day void via `voidError()`). Status labels/badges: `SALE_STATUS_LABEL` / `SALE_STATUS_BADGE`.
- **Credit notes** (ใบลดหนี้, `core/models/credit-note.model.ts`, decided 2026-10-04): returns of a paid POS bill from the day _after_ the sale (same day → void). The bill never changes; a `CreditNote` (`CN-YYYYMMDD-NNNN`) refers to it. Refund per line = its share of `amount` (discounts already in it, bill discount not re-checked; the last units take the exact remainder). Free goods are re-checked with `freeSets()` on what the customer keeps — kept free units no longer earned are deducted at `SaleLine.listPrice` (never twice). Money back in cash or through the bill's own methods up to what they took minus earlier refunds (`refundOptions()`). Returned goods go back at their sale COGS or are written off (serial → damaged); services never restock. `draftCreditNote()` / `creditNoteError()` are the single rule (form + mock). Admin only (page `/sales/:id/credit-note`). Sales-list totals subtract credit notes of the period. The bill's `status` stays `paid`; `Sale.returnStatus` (none / partial / full), `creditedTotal` and `creditNoteNos` are read-only, server-derived on every read from all its credit notes (`returnSummary()`) — the list shows a second badge (`RETURN_STATUS_LABEL` / `_BADGE`), the refunded amount under the total and a "มีใบลดหนี้" filter.
- **Exchanges** (ใบเปลี่ยนสินค้า, `core/models/exchange.model.ts`, decided 2026-10-05): swap units of a paid POS bill for the **same SKU and unit** — same price, so no money, no credit note, no new invoice; the bill never changes. Any staff member within `StoreInfo.exchangeDays` of the sale day (Settings; 0 = no limit; admins any time); `exchangeBlocker()` / `exchangeError()` are the single rule (form + mock). The replacement must be in stock **before** the exchange (`ctx.products`; returned units never count — same rule as the POS) and is issued **first**, like a sale (serial: own cost; others: current avg); only then does the old unit come back into stock (serial: own cost; others: the line's sale COGS share) or get written off (serial → damaged) — `costIn` / `costOut` are on the line, the bill's COGS stays. Serial warranty keeps counting from the sale day (`warrantyEnd()`). **The serial the customer holds is `currentSerial(sale, index, exchanges)`** — credit notes (`draftCreditNote(..., exchanges)`) and void return that one, never `line.serial` directly. `Sale.exchangeNos` is server-derived. Page `/sales/:id/exchange`, 80 mm `ExchangeReceipt` (`shared/components/receipt`), bill page `?printEx=<id>`.
- **Full tax invoice** (ใบกำกับภาษีเต็มรูป, `core/models/tax-invoice.model.ts`, decided 2026-10-04): issued on request instead of the abbreviated one — one per paid POS bill of a VAT-registered store (`taxInvoiceError()`, form + mock). Buyer details are typed on the invoice (no customer master); the buyer's head office / branch is needed only for VAT-registered buyers — `branchType: 'none'` (default for a national ID, `defaultBuyerBranch()`) prints nothing, show it via `buyerBranchLabel()`; a foreign buyer without a Thai tax ID uses `idType: 'passport'` (passport no. kept in `taxId`, no branch; `buyerIdError()` / `buyerIdLabel()` / `buyerIdShort()`, missing `idType` = `tax_id`); amounts always come from the bill; `Sale.taxInvoiceNo` is server-set; voiding the bill cancels it (`cancelledAt`); credit notes print the number valid when they were issued and never change (the bill page flags a cancelled one with its replacement via `invoiceRefState()`). Printed as original / copy on A4 (`TaxInvoiceDocument`, `printElement(el, 'A4')`) or 80 mm (`TaxInvoiceSlip`, `printElement(el)`), both in `shared/components/tax-invoice`; `StoreInfo.taxInvoicePaper` is the default (the POS uses it, the bill page can switch); VAT split via `invoiceTotals()`, total in words via `bahtText()` (`shared/utils/baht-text.ts`). Two ways: **with the sale** — the POS "ขอใบกำกับภาษีเต็มรูป" button collects the buyer (`BuyerDialog`, `checkoutBuyerError()`), `SalePayload.buyer` makes `POST /sales` issue it in the same request dated at the sale (`TaxInvoice.atSale`, no abbreviated invoice, the internal `POS-…` number is not printed; the POS prints the A4 invoice instead of the 80 mm slip); or **later** on page `/sales/:id/tax-invoice` (in place of the abbreviated one; no time limit). Wrong buyer details are never edited: admins **cancel and reissue** (`reissueError()`, page `?reissue=1`) — the old one gets `cancelledAt` / `cancelReason` / `replacedByNo`, the new one a new number (same sale day, same amounts, same `atSale`) and `replacesInvoiceNo`; `currentInvoice()` picks the valid one. Either way it is dated and numbered on the **sale day** (`INV-<sale day>-NNNN`; accountant's decision 2026-10-04) and `issuedAt` records when it was really issued. Once a bill has one, its 80 mm `Receipt` prints as a plain receipt referring to it.
- **Sales tax report** (รายงานภาษีขาย, `/sales/tax-report?month=YYYY-MM`, decided 2026-10-04): `buildSalesTaxReport()` (`features/sales/data/sales-tax-report.ts`) counts each sale's VAT once — bills sold while not VAT-registered and their credit notes are left out entirely (only `nonVatExcluded` → a heading note via `nonVatNote()`, B20); abbreviated invoices summarised per day and POS terminal with the terminal's POS ID in the note (bills with a full invoice issued _at sale_ are not counted as abbreviated), at-sale full invoices on their own line with the buyer, later full invoices (dated on the sale day) as uncounted reference lines (VAT already in the abbreviated one), voided = 0, credit notes negative in their month with the buyer of the invoice they quote (`CreditNote.buyer`, snapshot). Heading: tax month, seller name, tax ID, business place (`StoreInfo.placeName` → `placeName()`), branch — on screen/print and in the Excel; column headings repeat on printed pages. Printed landscape (`printElement(el, 'A4-landscape')`), Excel via `salesTaxReportXlsx()`.
- **Receipts** (decided 2026-10-04): shared `Receipt` (`shared/components/receipt`, 80 mm, stateless: `Sale` + `StoreInfo` + `copy`) — VAT-registered store → abbreviated tax invoice with VAT-able / VAT / exempt amounts and the bill's own `Sale.posId`. **Not VAT-registered** (B20, 2026-10-16): `priceCart()` takes `ctx.vatRegistered` and sets every line's `vat` to 0 (prices unchanged; POS hides "VAT ที่รวมอยู่"); the server snapshots `Sale.vatRegistered` (credit notes copy it) — read it with `soldWithVat()` (missing = registered, older data, not migrated). Such a bill is never a tax invoice (`taxInvoiceError()`), its credit notes take no VAT back, and `Receipt` / `CreditNoteReceipt` print by the document's snapshot, not the store's current setting. `StoreInfo` (`store-info.model.ts`, `storeInfoError()`, `GET/PUT /settings/store`) is edited in the Settings menu (admin only, live preview). Print with `printElement(el)` (`shared/utils/print-element.ts`; `'A4'` / `'A4-landscape'` for A4 documents): hides everything else, strips ancestors' spacing (`.print-chain`), sizes `@page` to the element, cleans up on `afterprint`; keep the element laid out off-screen with the global `.print-stage` class (not `display: none`).

Printing: global `@page` A4 margin 0; wrap on-screen controls in `.no-print`; `LabelSheet` adds `html.print-labels` so the layout padding is dropped. The sidenav content is a scroll container — global print CSS un-clips it so all pages print.
- **Sale prices live only in `SkuPrice` periods** (`core/models/price.model.ts`, endpoints `/prices`). `Product.currentPrice` is read-only, derived by the server from today's period (`null` = "ยังไม่กำหนดราคา", counts as 0 in stock value); the SKU form has no price field. Use the helpers `todayIso/toIsoDate/fromIsoDate/priceStatus/effectivePrice/findOverlap` (shared by UI and mock) — never `new Date('YYYY-MM-DD')` (UTC shift). ## Conventions

- Standalone components, `ChangeDetectionStrategy.OnPush`, `inject()` (no constructor injection), `input()`/`output()`/`viewChild()` signal APIs, `@if`/`@for` control flow.
- State: `signal` / `computed` in services; expose read-only via `.asReadonly()`. No NgRx.
- Forms: Reactive forms via `NonNullableFormBuilder`.
- Route params bind to component inputs (`withComponentInputBinding()`), e.g. `readonly id = input<string>()`.
- Imports use aliases `@core/*`, `@shared/*`, `@layout/*`, `@features/*`, `@env/*`; relative imports only within the same feature/folder.
- Styling: use Material system tokens (`var(--mat-sys-*)`), not hard-coded colors, so dark mode (`html.dark-theme`, toggled by `ThemeService`) works.
- Global helper classes in `styles.scss`: `.stat-grid` (layout for `<app-stat-card>`), `.filter-row` (search/filter controls above a table), `.badge` + `.badge-success|warn|error` (status pills). Reuse them instead of per-component copies.
- Money: `currency: 'THB' : 'symbol-narrow' : '1.0-0'`; dates: `thaiDate` pipe.
- mat-table rows are untyped (`let x` is `any`), so strict templates cannot index a `Record` with them — use a typed helper method (e.g. `statusText(sale: Sale)`).
- Icons: Material Symbols Outlined (set as default font set in `app.config.ts`).
- UI text is Thai; code, identifiers and comments are English.
- Selector prefix `app-` (components) / `app` camelCase (directives).

## Gotchas

- TypeScript 6: don't add `baseUrl` to tsconfig (deprecated); `paths` are relative to `tsconfig.json`.
- `CanMatchFn` in Angular 22 takes 3 args (`route, segments, currentSnapshot`) — tests must pass a third.
- No `@angular/animations` package; Material 22 doesn't need it — don't add `provideAnimationsAsync()`.
- Initial bundle budget is 600 kB warning / 1 MB error (`angular.json`). Keep heavy Material modules out of eagerly loaded code (`core` services, `app.ts`).
- `DatePipe` / `formatDate` in a feature moves `@angular/common`'s locale formatting (~9 kB) into the shared _initial_ chunk — use the `thaiDate` pipe or a small helper instead; compare "Initial total" before/after a change.
- `AuthService.logout()` and login success call `document.location.assign` (inject `DOCUMENT`); in tests provide a stub `DOCUMENT` with `location.assign = vi.fn()`.
- Tests use Vitest globals (`vi`, `describe`, …); HTTP tests use `provideHttpClientTesting()` and `HttpTestingController`.
